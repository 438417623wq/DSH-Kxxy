# 九项环境问题修复（2026-11-18，v0.9.65）

清单里的 9 条分三类：**5 条是运行时的真缺陷**（能修，已修）、**1 条是 Android
平台限制**（只能降级干净）、**3 条是能力缺失**（不是 bug，需要另立项目）。
把三类混在一起谈「全部修复」会得出错误结论，所以先给这张表。

## 1. Ruby —— 两条通道必须分开判断

`buildEnv` 里原本是两行：

```kotlin
"RUBYLIB=${rubyLibPath(root)}",
"RUBYOPT=-rrubygems",
```

问题不在 `rubyLibPath` 算得对不对（它扫 `<root>/lib/ruby` 与每个扩展的
`lib/ruby`，是对的），而在**时机**：`RUBYLIB` 是引擎进程 `execve` 时的一
次性快照，而 `ruby` 是扩展池里的东西 —— 用户装完 ruby 扩展再开终端，环境
里那条 `RUBYLIB` 还是「装之前」算的，于是 `$LOAD_PATH` 只剩 `libruby` 里
编译期写死的

```
/data/data/com.termux/files/usr/lib/ruby/4.0.0
```

（`rewrite_prefixes` 跳过 ELF，这些字符串在设备上一个都不存在）。而
`RUBYOPT=-rrubygems` 的 `-r` 是**启动即执行**：找不到文件就 abort，
`ruby -e 'puts 1'` 都跑不了 —— 这就是「Ruby 完全不可用」而不是「rubygems 不
可用」的原因。

### 一个容易漏的细节：`lib/ruby` 是软链，版本段不能省

设备上 `<engine>/lib/ruby` 是 **`extensions/ruby/lib/ruby` 的软链**，而
`rubygems.rb` 在版本目录里（`4.0.0/rubygems.rb`）。所以「把 termux 旧前缀从
`$LOAD_PATH` 里清掉」**不等于修好**：只要 `RUBYLIB` 停在父目录 `lib/ruby`，
`require "rubygems"` 依然找不到。真机对照：

```
RUBYLIB=…/engine/lib/ruby                        → cannot load such file -- rubygems (LoadError)
RUBYLIB=…/engine/lib/ruby/4.0.0:…/aarch64-linux-android → ok 4.0.20
```

`rubyLibPath` 已经按目录扫出版本段与架构段（不写死 `4.0.0`），本次只是把
「不存在的目录不收」补上；真正致命的仍是那条无条件 `RUBYOPT`。

改法分两层：

- `EngineConfig.buildEnv`：`RUBYLIB` 只放**磁盘上真实存在**的目录；
  `RUBYOPT` 改为条件注入（`rubyRubygemsReachable`，逐条扫 RUBYLIB 找
  `rubygems.rb`）。加载不到就不给 —— 宁可 `defined?(Gem)` 是 nil，也不要
  整个 ruby 起不来。
- `userShellInitContent`（`# kxxy-shell@6`）：按磁盘现状重算 `RUBYLIB`
  （合并视图 + 每个扩展的 `lib/ruby`，含 `site_ruby`/`vendor_ruby`/架构目录），
  并按同一判据**补或摘** `RUBYOPT`。判据是「有没有任何一条目录能提供
  `rubygems.rb`」，不是「变量是否为空」—— 变量非空但全是死路径同样要重算；
  只看第一条会误判，因为 `site_ruby` 通常排在版本目录前面。

真机（`run-as`，环境不手动给 RUBYLIB，交给 `.bashrc`）：

```
RUBYOPT=[-rrubygems]
json={"a":1}
gem=4.0.20 / bundle=4.0.20 / irb 1.16.0
```

## 2. gdb —— 判据与时机一起修

`ensureGuileCcacheFresh` 原本存在两个问题：

1. **时机**：只挂在 `maintainAfterHealthy()`（引擎 Healthy 之后的异步维护），
   用户在它跑完前敲 gdb 就是 137 秒超时。
2. **同源**：ccache 与 share 各自 `firstOrNull { it.isDirectory }`，中间态下
   会拿合并视图的 `.go` 去比扩展树的 `.scm`。

现在：全量扫描移到启动关键路径（344 次 stat，无写入）与全量安装收尾各跑一次；
两棵树**成对**取自同一来源；补 `orphan`（有 `.go` 没 `.scm`）与
`setLastModified` 失败计数 —— 后者以前是静默失败，日志正常但 gdb 依旧慢。

`.bashrc` 的兜底从「目录存在」改为「关键 `.go` 文件存在」，并补 mtime 比较：
`.scm` 比 `.go` 新就 `touch` 对应的 `.go`。只处理 `ice-9/boot-9` 与
`system/repl/*` 这几个 —— 它们正是那 141 秒的来源，常数级开销。

真机：`gdb --version` → `GNU gdb (GDB) 18.1`，`elapsed=0s`。

## 3. 终端 dsh —— 一个 flag，但坏的不是「全部子命令」

App 主进程 `EngineProcess.spawn` 一直带着 `--expose-internals`（因为运行时的
`node-addon-require-builtin` 被换成了纯 JS shim，要 require `internal/*`），
但 `RuntimeInstaller.ensureDshWrapper` 生成的 `bin/dsh` 漏了。于是 **App 内
一切正常，只有终端坏** —— 这种「只在一侧坏」的症状最容易被误判成环境问题。

要说准边界（原描述「全部子命令 exit 1」是不成立的）：

- `dsh --version` / `dsh --help` **本来就能过**：它们只解析命令行，不进 host
  preparation，不碰 `internal/*`。
- 真正挂掉的是 `web` / `headless` 这类要**启动 host** 的入口，报
  `host preparation failed: Cannot find module 'internal/modules/esm/loader'`。
- `dsh plugin list` 的 `error: required option '--profile <name>' not specified`
  是**用法错误**，与这个 flag 无关（原生 dsh 同样要求 `--profile`）。

真机对照（同一台设备、同一个 `bin.js`）：

```
$ bin/dsh web          → 走到插件激活，只因 EADDRINUSE 3080 退出（引擎已占端口）
$ node bin.js web      → dsh: host preparation failed:
                         Cannot find module 'internal/modules/esm/loader'
```

前者说明 host preparation 已经过了，后者是同一个缺 flag 的现象 —— 这就是修复
有效的直接证据。`dsh --help` / `dsh plugin --help` / `dsh web --help` /
`dsh headless --help` 现在全 rc=0。

## 4. venv —— 跨包版本契约

`ensurepip/__init__.py`（python 包）里：

```python
_PIP_VERSION = "26.2.1"
... / 'pip-{_PIP_VERSION}-py3-none-any.whl'
```

而那个 wheel 来自**另一个包** `python-ensurepip-wheels`。两个包各自跟索引走，
python 被钉在 3.14.8、wheel 包却漂到 3.14.10，于是 `_bundled/` 里只有
`pip-26.2.2-py3-none-any.whl`，`_bootstrap()` 找不到精确文件名 → assert →
`python3 -m venv` exit 1、建出的环境里没有 pip。解包核对（`open_data_tar`）：

```
python-ensurepip-wheels 3.14.8  → _bundled/pip-26.2.1-py3-none-any.whl
python-ensurepip-wheels 3.14.10 → _bundled/pip-26.2.2-py3-none-any.whl
```

三处改动：

1. `tools/lib/seeds.mjs`：`python-ensurepip-wheels` 与 `python` **成对**钉在
   3.14.8（缓存里有这个 deb，离线可用）。
2. `tools/lib/python-runtime.mjs`：`verifyPythonRuntime` 增加一致性断言 ——
   从 `__init__.py` 读出 `_PIP_VERSION`，要求 `_bundled/pip-<ver>-py3-none-any.whl`
   存在，且该 wheel 内部中央目录里真有 `pip-<ver>.dist-info/METADATA`
   （文件名与内容都要对）。不一致时**构建失败**，而不是改名糊过去。
3. `RuntimeInstaller`：新增运行时锚点 `ensurepipWheelMatches()`。

第 3 条是这次唯一新增的**安装期判据**，理由值得记一笔：前十几个锚点用的是
「常量标记 + 版本号」，而这是一处**已有文件的内容变化** —— 不新增文件、不动
`RUNTIME_VERSION`。第一次装 v0.9.65 时正因如此走了快路径，wheel 仍是 26.2.2。
所以这条锚点不用常量，而是**直接比对两个文件**：期望的 wheel 名由
`_PIP_VERSION` 现算。下次 python 包再漂移会自动判假，不需要人记得升标记。

真机日志与结果：

```
W KxxyRuntime: runtime probe: ensurepip 的 pip wheel 与 _PIP_VERSION 不一致，强制重装
I KxxyRuntime: runtime install complete
```

```
pip files=3
pip 26.2.1 from .../v2/lib/python3.14/site-packages/pip (python 3.14)
```

## 5. PDF —— 引擎在，标准名没建

先纠正一处早前的误判：报错 **不是**「找不到 pdflatex」，而是
`execvpe: permission denied` —— 名字在 `PATH` 上存在，但执行不了；也不该说
「texlive 只装了 paper/sfconv 这类辅助程序」。设备实况：

```
extensions/texlive/bin/texlive/   883 个可执行
  ├─ pdftex    0755  2.0 MB
  ├─ pdflatex  -> pdftex        （相对软链）
  ├─ latex / xelatex / lualatex / xetex / luahbtex 全在
```

真正缺的是 `<engine>/bin/` 下的**入口名**：`texlive` 在**扩展池**
（`POOL_ITEMS`）里，不是预装；标准名靠 `texlinks` 这个 shell 脚本建，它依赖
`kpsewhich` 与 perl 环境，一旦 rc!=0 就一个名字都不建。旧实现的
`if (!source.isFile) continue` 又只认实体文件，把四个名字全跳过 —— 于是设备上
只剩 `pdftex`/`tex`/`luahbtex`，看起来像「没装 PDF 引擎」。

新增 `TEX_ENGINE_OF`：标准名缺失时直接从引擎本体建软链
（`pdflatex`/`latex` → `pdftex`，`xelatex` → `xetex`，`lualatex` → `luahbtex`），
并且**逐名判定**，不再因为一个名字拿不到就整批放弃。TeX 按 `argv[0]` 的
basename 决定读哪个 `.fmt`，所以「软链名 = 格式名」必须由文件名承担，参数替代
不了。

修复后设备上：

```
bin/pdflatex -> …/extensions/texlive/bin/texlive/pdflatex
bin/latex    -> …/extensions/texlive/bin/texlive/latex
bin/xelatex  -> …/extensions/texlive/bin/texlive/xelatex
```

中文这一层单独处理：pandoc 的默认 `mainfont` 是 lmroman，没有任何 CJK 字形，
于是每页刷 `Missing character`、PDF 里那行是空白。新增
`ensurePandocCjkDefaults`，在 `$HOME/.local/share/pandoc/defaults/` 落一份
`kxxy-cjk.yaml`（`pdf-engine: xelatex` + 指向随包 `NotoSansSC-Regular.ttf` 的
`mainfont`/`Path=`），用法：

```sh
pandoc -d kxxy-cjk in.md -o out.pdf
```

不用 `CJKmainfont`（要 `xeCJK`）：随包的 TeX 树是精简档，`xeCJK` 不保证在；
换 `mainfont` 只需要 `fontspec`，依赖面最小。

真机：

```
latex.fmt=…/.texlive/texmf-var/web2c/latex.fmt
pdflatex.fmt=…/.texlive/texmf-var/web2c/pdflatex.fmt
pdflatex t.tex → Output written on t.pdf (1 page, 22057 bytes)
xelatex  c.tex → 0 个 Missing character
pandoc h.html -o h.pdf → 66493 B
pandoc -d kxxy-cjk m.md -o m.pdf → 7709 B，pdftotext 回读：
    中文标题 / 这是一个 Markdown 转 PDF 的测试。 / ・ 列表一 / ・ 列表二
```

`typst` / `wkhtmltopdf` / `weasyprint` 仍然没有 —— 它们不是「PDF 引擎坏了」，
而是没打包（见第 9 条）。HTML → PDF 走 `pandoc`（内部 xelatex）可通。

## 6. 硬链接 —— 平台限制，只做降级

`ln` 在 app 私有目录里报 `Permission denied`：SELinux 拒绝 `link(2)`。早前
`tools/lib/assemble.mjs` 的注释写成「既禁硬链接也禁符号链接」，**这是错的**，
`bin/pdflatex -> pdftex` 这类软链在设备上正常工作（`collectBins` 就是
`symlinkSync`）。注释已更正。

能做的只有「降级得干净」：`ensurePnpmImportMethod` 写 `~/.npmrc` 的
`package-import-method=copy`，让 pnpm 不再先失败一轮 hardlink 再降级。
`rsync --link-dest`、`cp -l`、`git worktree` 共享对象走同一条 `link(2)`，同样
不可用 —— 这是能力边界，不是配置问题。

## 7. 时区 —— `LANG` 不是解药

三缺：`TZ` 未设、`/etc/localtime` 在 Android 上不存在、`LANG`/`LC_ALL` 为空。
但 **JVM 不读 `LANG`**（那只影响 `user.language`），它只认 `TZ` 与
`-Duser.timezone`。所以：

```
TZ=<系统 Olson ID>            # 给 libc 系工具（date/ls/git log）
-Duser.timezone=<同一 ID>      # 给 JVM
```

取值用 `TimeZone.getDefault().id`（`Asia/Shanghai`），**不写死 `GMT+8`** ——
写死偏移在夏令时地区是错的。引擎进程实测：

```
TZ=Asia/Shanghai
JAVA_TOOL_OPTIONS=… -Duser.timezone=Asia/Shanghai …
java ... user.timezone = Asia/Shanghai
```

用户改系统时区后需要重启引擎进程才会生效（env 是 `execve` 的一次性快照）。

## 8. sherpa-onnx-node —— 未修，只放开了误杀

真机 `lib/node_modules/sherpa-onnx-node/` 里只有 JS（`addon.js`、
`sherpa-onnx.js`、各任务入口），**没有 `sherpa-onnx.node`，也没有
`sherpa-onnx-android-arm64/`**。上游只发布 `sherpa-onnx-linux-arm64`，那是
glibc、在 bionic 上 dlopen 必失败，不能当替代品。

本次只改了一处**规则**：`isPlatformSpecific` 以前把「声明了 os/cpu 的包」一律
排除，连将来真正面向 Android 的包也会被静默丢弃；现在 `declaresAndroid`
（`os: ["android"]`/`bionic`，或包名带 `-android-`）例外放行。今天闭包里没有
这种包，所以**行为不变**；等上游发了 android-arm64 预编译（或我们自己补 NDK
构建），它必须能进包。

要真修就得交叉编译 sherpa-onnx 的 Android 绑定并打进 runtime —— 那是独立项目，
不在这批改动里。

## 9. 前端与科学计算工具 —— 能力缺失，不是 bug

真机实测（`command -v`）：`tsc`/`vite`/`esbuild`/`webpack`/`prettier`/
`eslint`/`gfortran`/`julia`/`dotnet`/`deno`/`zig`/`valgrind`/`perf` 全部不存在。

它们不是「坏了」，是运行时镜像**没有打包**。补法各不相同：

- 前端 CLI（tsc/vite/prettier/eslint）：npm 侧的锁版本依赖 + 离线缓存 +
  bin 包装器；esbuild/rollup 的**原生组件**还要单独核 Android 支持 ——
  manylinux 与 linux-musl 的构件在 bionic 上不能用。
- 科学计算（scipy/sklearn/torch/opencv）：必须走 Android/arm64 原生依赖与 ABI
  验证，不能直接塞 manylinux wheel。现有预装声明只有
  `numpy`/`pandas`/`matplotlib`/`pillow`/`cryptography`/`lxml`/`psutil`。
- Julia / .NET / gfortran：JDK 那样的独立工具链级项目。
- `perf`/`valgrind`/`ltrace`：还涉及内核、ptrace 与平台支持，不能保证
  「补包即可用」。

这一条**不作为 bug 修复**，需要按能力包单独立项、逐项验收。

## 真机验收

设备：Redmi K60 Pro（`22127RK46C`，Android 13），`app.kxxy` 0.9.64 → 0.9.65，
APK `2,037,937,551 B`，SHA-256 见 `dist/`。运行时就地重装一次（820 MiB
zip 解包 45 秒），扩展目录未被动过。

  「default gem 找不到」应从这条查。
