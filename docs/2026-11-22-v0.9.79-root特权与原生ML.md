# v0.9.79：把三条「只能降级」的路走通（root 特权、真实 PMU、原生 ML）

v0.9.78 只做了降级语义收口：指针、perf、Python 三处「做不到」都给出确定的行为
和确定的退出码，但**事情本身仍然做不到**。这一版把三件事真正做完：

| 问题 | v0.9.78 的状态 | v0.9.79 |
| --- | --- | --- |
| `link(2)` | app 域 errno 13，`ln` exit 1，`rsync --link-dest` 退化成复制 | 已 root 时显式走 root 域，真实硬链接 |
| `perf_event_open` | 21 个计数器全 EACCES，只能 rusage/ptrace 降级 | 已 root 时真实 PMU，`stat`/`record`/`list` 全通 |
| 原生 Python 3.14 | 缺 sklearn、cv2 | 两个包都在真机编成 bionic 轮子并内置 |

三条路径共用一条原则：**默认行为一个字不改**，所有特权路径都是显式 opt-in。
没 root、用户拒绝授权、或用户根本不关心，运行结果与 v0.9.78 完全一致。

## 1. 硬链接：域策略，不是文件系统能力

先证伪一个容易走错的假设：`/data` 是 f2fs，f2fs 支持硬链接，但设备上
`link()` 返回 `EACCES`。用同一份 C 程序在两处跑：

```
# app 域（uid 10398, u:r:untrusted_app_27）
link() = -1  errno=13 (Permission denied)

# root 域
link() = 0   dev=65060 ino=3006205 nlink=3 same=1
```

同一个文件、同一个系统调用、同一台设备，唯一变量是 SELinux 域。结论：
`untrusted_app_27` / `runas_app` 域都被 sepolicy 挡在 `link`/`linkat`/`FICLONE`
之外，用户态没有任何绕法（`FICLONE` 也是 EACCES，reflink 在 f2fs 上根本不存在）。

另外记一笔坑：glibc 容器里 `os.link` 会「成功」，那是 proot `--link2symlink`
的假象 —— **不能用它判断设备能力**，只有 bionic 原生解释器或 C 程序的结果算数。

### 实现

新增 `libexec/kxxy-tools/kxxy-root.py`：一个只认固定四个操作
（`ln` / `perf` / `rsync` / `exec`）的 root 桥。参数经 `shlex.join` 转义后交给
`su -c`，root 侧再用 `env -i` 固定环境（`HOME=/`、`PATH=$root/bin:/system/bin`、
`LD_LIBRARY_PATH=$root/lib`、`KXXY_ROOT_OWNER`），**不透传**
`PYTHONPATH` / `LD_PRELOAD` / 任何调用者环境变量。

- `bin/ln`：`KXXY_LN_ROOT=1` → 走 root 桥；默认 0 → 原样 coreutils。
- `bin/kxxy-rsync`：`KXXY_RSYNC_ROOT=1` → root 桥。此模式下已是真实硬链接，
  因此显式拒绝 `KXXY_RSYNC_LINK_MODE=symlink`（exit 1）和
  `KXXY_RSYNC_DEDUP`（exit 2），不静默忽略互斥选项。
- `bin/kxxy-root -- <cmd>`：任意命令直接以 root 跑，同样过 `env -i`。

真机验证：

```
$ KXXY_LN_ROOT=1 ln a b        →  b inode 3006205, nlink 2
$ KXXY_RSYNC_ROOT=1 kxxy-rsync -a --link-dest=basis src/ dst/
  basis/same 与 dst/same → 同为 inode 3233809, nlink 2, cmp 一致
```

`KXXY_SU` 必须是绝对路径（防止 PATH 劫持）；`--root-active` 标记防递归。

验收时抓到一个只在「显式传 `--`」时才出现的缺陷：`bin/kxxy-root` 自己已经在
参数里插了一层 `--`（`... kxxy-root.py exec -- "$@"`），用户在命令行再按文档写
`kxxy-root -- id` 就成了两层，脚本只剥一层，于是它去执行一个名叫 `--` 的程序：

```
kxxy-root: cannot execute --: [Errno 2] No such file or directory: b'/system/bin/--'
```

修法是两头都收紧：包装器不再插 `--`，脚本改成 `while args[0] == "--"` 循环剥，
并加了「双层 `--` 剥完为空要报错」的回归用例。注意这个 bug **不会**体现在
`KXXY_LN_ROOT` / `KXXY_PERF_ROOT` / `KXXY_RSYNC_ROOT` 三个包装器上 —— 它们不传
`--`，所以只有 `kxxy-root` 手写路径会踩到。

## 2. perf：PMU 在 root 域是通的

`perf_event_paranoid = -1`，但 app 域仍 EACCES —— 又是 sepolicy。root 域下
21 个计数器全部打开。

```
$ KXXY_PERF_ROOT=1 perf stat -e task-clock,page-faults,context-switches,cycles,instructions -- <cmd>
    15,929,530      cycles
    17,267,054      instructions
$ KXXY_PERF_ROOT=1 perf record -o perf.data -- <cmd>   → 299 samples, report 正常符号化
$ KXXY_PERF_ROOT=1 perf list                            → 全部 PMU ✓
```

三个必须处理对的细节：

1. **不允许悄悄降级。** root 桥对 `perf` 操作强制 `KXXY_PERF_MODE=pmu`，
   `KXXY_PERF_ROOT=1` 与 `KXXY_PERF_MODE=fallback` 同时给直接 exit 2 —— 用户
   显式要了 PMU，就不能拿到 rusage 数据还以为是真的。
2. **perf.data 所有权要还回来。** root 写出的文件属主是 root，应用读不了也删不
   掉。`restore_record_owner()` 在 `finally` 里按 `KXXY_ROOT_OWNER` 做
   `os.chown(..., follow_symlinks=False)`。真机确认产出文件属主是
   `u0_a398:u0_a398`。
3. **`record` 不能吃掉目标退出码。** 旧实现用 `waitpid(WNOHANG)` 判活，status
   被丢掉。改为 `poll_child()` 保留 status，`record -- /system/bin/false`
   返回 1。`-p` 抓不到样本时 rc 1（不是 0）。

`perf.py` 版本号 1.1 → 1.2，策略提示里加了 root 一行。

一个容易误判的现象：`adb shell run-as` 落在 `runas_app` 域，那个域**本来就有**
PMU 权限，所以用 adb 验收时 `perf stat -e cycles` 不设 `KXXY_PERF_ROOT` 也能出
数。真正的 app 域（`untrusted_app_27`）才 EACCES。结论是 root 路径服务的是
**App 进程内**发起的 perf，而不是 adb 调试路径 —— 两者不能互相外推。

## 3. 原生 Python 3.14：sklearn + cv2

默认 `python3` 是 glibc 3.12 容器，六包齐全；`python3.14` 是 bionic 原生，之前
只有 numpy/scipy/pandas/torch。缺的两个包都用真机上的 clang/NDK 编成了
`cp314-cp314-android_24_arm64_v8a` 轮子。

### 3.1 scikit-learn 1.9.1

`Root-Is-Purelib: false`，`Tag: cp314-cp314-android_24_arm64_v8a`，sha256
`5ebf5af3645a011cce4dd3ea1c4f5914ca90cc4eba7e8a012333a6db202edc03`。

构建中踩到的四个坑（都不是「配个 CFLAGS」能过的）：

- `Preparing metadata` 失败：sklearn 的 `version.py` shebang 是
  `#!/usr/bin/env python3`，Android 没有 `/usr/bin/env`。重打包 sdist，改成
  `/system/bin/env`。
- `Compiler clang cannot compile programs`：缺 `asm/types.h`。从 NDK sysroot 取
  `aarch64-linux-android/asm` 解到 `$PREFIX/include/asm`。
- `'climits' file not found`：要 `CPLUS_INCLUDE_PATH=$PREFIX/include/c++/v1`。
- Termux 的 `ninja` 二进制把 shell 路径硬编成
  `/data/data/com.termux/files/usr/bin/sh`，在 app 域根本不存在（`strace` 看到
  `execve(...) ENOENT`，ninja 只报 `code=127`）。把它等长替换成
  `/system/bin/sh` 后 151/151 目标过。

### 3.2 opencv-python-headless 5.1.0.95

sha256 `0828dc14a65341955427c7bf3058af5d59dda037e879235431be1a287f04bccc`，
6.2 MiB，依赖 `libpython3.14.so` / `libavif.so` / `libz.so.1` /
`libc++_shared.so`（都在 `engine/lib`）。构建脚本与补丁随仓库保存：
`tools/prebuilt/native-ml/patch-opencv-android.py`（给 sdist 打两处补丁）+
`tools/prebuilt/native-ml/build-opencv-android.sh`（设备上跑 pip 构建）。

OpenCV 上游**在 CMake 层直接禁掉 Android 的 Python 绑定**：

```cmake
# modules/python/CMakeLists.txt
if(ANDROID OR APPLE_FRAMEWORK OR WINRT)
  ocv_module_disable_(python3)
  return()
endif()
```

这条守卫是为「用 Android SDK、只要 Java 绑定」的正规流程写的；在设备上原生编译
时它是纯粹的阻碍。补丁去掉 `ANDROID` 一项，保留另外两个。

去掉守卫后第二层问题：Android 分支里 `find_package(PythonLibs)` 被整段跳过，
于是 `PYTHON3_INCLUDE_PATH` / `PYTHON3_NUMPY_INCLUDE_DIRS` 得手工喂：

```
-DPYTHON3_INCLUDE_PATH=$PREFIX/include/python3.14
-DPYTHON3_NUMPY_INCLUDE_DIRS=$SP/numpy/_core/include
-DPYTHON3_PACKAGES_PATH=$SP
-DPYTHON3_LIMITED_API=OFF
-DOPENCV_FORCE_PYTHON_LIBS=ON      # 见下
```

`OPENCV_FORCE_PYTHON_LIBS=ON` 是关键的一行。默认（非 Windows/非 Apple）OpenCV
**不链接 libpython**，靠主可执行文件导出 Python C API 符号 —— 桌面 Linux 上
CPython 是静态链进 `python` 的，符号天然在全局作用域里。我们的
`engine/bin/python3.14` 只有 4.6 KB，Python 全在 `libpython3.14.so` 里，Android
linker 在给 dlopen 出来的库解析符号时拿不到它：

```
ImportError: dlopen failed: cannot locate symbol "_Py_NoneStruct"
             referenced by ".../cv2/cv2.cpython-314-aarch64-linux-android.so"
```

对比 `numpy._multiarray_umath` 的 DT_NEEDED 里明明白白写着 `libpython3.14.so`
（Termux 的 python-config 会加 `-lpython3.14`），而 cv2 的 DT_NEEDED 里没有 ——
所以不是「Android 不支持」，是「没链」。

最后一道：`cmake/package/install_package.cmake` 把 PEP 561 的 `py.typed` 和
`cv2/typing/*.py` 当硬依赖，而 typing stubs 生成器在本机构建里产出 0 个 `.pyi`
（`cv2/typing` 是空目录），于是 `install` 在 `cv2.so` 已经装好之后才 abort。两处
glob 改成 `OPTIONAL` —— 类型存根只影响 type checker，不影响运行时。

真机结果：

```
cv2 5.1.0 / numpy 2.5.4
connectedComponentsWithStats → 3 个连通域, stats (3,5)
imencode(".png") → 411 B, imdecode 回来逐像素相等
Canny → 248 个边缘点；calcHist 8 bin 合计 6144 = 64×96 ✓
sklearn 1.9.1 + cv2 同一进程联测：LinearRegression coef=2.0000 intercept=3.0000
KMeans / PCA / Pipeline 正常
```

### 3.3 打包

`tools/prebuilt/native-ml/` 放两个 wheel，`tools/lib/pydeps.mjs` 的
`NATIVE_ML` 列了文件名 + sha256 + anchor，构建时校验哈希、解包进
`lib/python3.14/site-packages`，`build-runtime.mjs` 再断言六个锚点文件都在包里
（`REQUIRED_NATIVE_ML`），少一个直接构建失败。

纯 Python 依赖补了 `narwhals`（sklearn 直接 import）和 `cloudpickle`
（joblib 序列化路径）。

### 3.4 提示语要跟着改

`_kxxy_hint.py` 原来对 `sklearn` / `cv2` 抛「只有 manylinux 轮子，装不上」——
现在这话是错的。改成只覆盖**确实没有 Android 构建**的那批
（tensorflow / xgboost / lightgbm / catboost / onnxruntime / torchvision /
torchaudio），并且把 `ImportError` 换成 `ModuleNotFoundError`（带 `name`），
免得把用户 `except ModuleNotFoundError` 的分支打穿。

## 契约与开关一览

| 开关 | 默认 | 作用 |
| --- | --- | --- |
| `KXXY_LN_ROOT` | 0 | `bin/ln` 走 root 域创建真实硬链接 |
| `KXXY_RSYNC_ROOT` | 0 | `kxxy-rsync` 走 root 域，`--link-dest` 真去重 |
| `KXXY_PERF_ROOT` | 0 | `perf` 走 root 域真实 PMU（与 `KXXY_PERF_MODE=fallback` 互斥） |
| `KXXY_PERF_MODE` | auto | `auto` / `pmu` / `fallback`（1.2 起不变） |
| `KXXY_SU` | 空 | root 桥用的 su 绝对路径 |

`PATCHSET_MARKER` → `kxxy-patchset@37`（三处同步：`build-runtime.mjs`、
`RuntimeInstaller.kt`、`test-runtime-capability-contracts.mjs`）。
