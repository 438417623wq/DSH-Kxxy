## 1. P1：脚本模板的 CRLF 会让「预置」永远失败

### 现象

`python -V` 报 `kxxy-python: glibc Python is missing…`（exit 127）；
`dotnet` / `julia` / `wkhtmltopdf` 首次使用都报
`…/extensions/glibc/bin/kxxy-glibc-provision: No such file or directory`。

### 根因

`kxxy-glibc-provision` 163 行全是 CRLF。shebang 变成 `#!/system/bin/sh\r`，
内核 exec 时去找一个叫 `sh\r` 的解释器 —— 报的是 `No such file or directory`，
于是所有人都以为"脚本不在了"。

### 为什么提交前看不出来

`.gitattributes` 里 `* text=auto eol=lf` 让 git 在读写时都做归一化：
`git show :<path>` 是 LF，`git diff` 也是空的，**只有工作区那份文件是 CRLF**。
而 `build-runtime.mjs` / `asset-pack.mjs` 是直接读工作区文件打进的包 ——
坏字节就这样进了 APK，一路没人拦。

### 做法

新增 `tools/lib/script-source.mjs`：所有构建期脚本模板都走 `readScriptText()`
读入，发现 `\r` 就归一化成 LF，并在构建日志里大声警告（带文件名与行数）。
归一化后的字节**正是 git 索引里的那份**，所以不影响产物正确性；源文件该修还是要修。

接入点（三处，覆盖所有会被设备 exec 的模板）：

- `tools/lib/asset-pack.mjs` 的 `wrapperBody()` / `toolBody()`（扩展 `bin/*` 垫片）；
- `tools/lib/python-default.mjs`（`python-default.py` 与 `kxxy-glibc` 分派器）；
- `tools/build-runtime.mjs` 的 `kxxyToolScript()`（`libexec/kxxy-tools/*.py`）。

测试在 `tools/test-runtime-capability-contracts.mjs`：① 扫描
`tools/prebuilt/{wrappers,kxxy-tools}` 下所有 `.sh`/`.py` 断言无 CR；② 断言三处
读模板都经过 `readScriptText`。

### 验证（真机）

`sh -n` 通过、直接 exec 打印用法（rc=2，不再是 127），随后：

```
python 3.14.8 / kxxy-py 3.12.3（glibc 容器）/ dotnet 8.0.134
julia 1.11.7 / wkhtmltopdf 0.12.6
numpy 2.5.4 · sklearn 1.9.1 · cv2 5.1.0 · pandas 3.1.1 · torch 2.15.0
```

## 2. P2：zig 只能在 `bin/` 看着，编译不了

### 根因

Termux 的 zig deb 里 `usr/bin/zig` 本来链到 `usr/lib/zig/zig`。`poolextract.py`
出于「设备端 tar 只认文件、不认链接」的约定把软链**物化**成副本，于是
`extensions/zig/bin/zig` 是 171 MB 的实体文件，真身在
`extensions/zig/lib/zig/zig`。

zig 找标准库是按**可执行文件所在目录**推的（`exe/../lib/zig`、`exe/../lib`）：
副本在 `bin/` 下时两个候选都落空 → `unable to find zig installation directory`。
直接跑 `lib/zig/zig` 就正常，因为它的 `exe/..` 正好是 SDK 根。

### 做法

`plugins/kxxy-host/lib/extinstall.mjs` 的 `relinkShadowedLauncher()` 扩一条规则：
`bin/<name>` 与 `lib/<name>/<name>` 同大小（≤4 MiB 再比内容）就把副本换回**相对软链**
`../lib/<name>/<name>`。这跟它原本处理的 `opt/<pkg>/bin/<name>` 是同一类物化副本，
只是布局不同。建链失败时把内容写回去，不留空位。

副作用是顺带省掉一倍磁盘（171 MB）。`test-extinstall.mjs` 新增 `[4c]` 用例钉住
「变软链 / 指向 `../lib/zig/zig` / 标准库还在原位」。

### 验证（真机）

```
zig version        → 0.17.1
zig build-obj add.zig -femit-bin=add.o   → rc=0，产出 3,855,872 B 对象文件
zig cc -target aarch64-linux-musl -o hello hello.c && ./hello
                   → hello from zig cc
```

**边界**：裸 `zig cc`（不带 `-target`）仍会报 `LibCStdLibHeaderNotFound` ——
zig 不自带 bionic 头，默认目标就是 android。要当 C 编译器用必须显式给
`-target aarch64-linux-musl`（或 `-gnu` 配 sysroot）。这是 zig 的设计，不是环境坏。

## 3. P2：`dsh headless` 的两堵墙

### 第一堵：TLS 一个证书都没加载

Termux 编的 curl/node 把 CA 路径**编译期**钉死在
`/data/data/com.termux/files/usr/etc/tls/cert.pem`。引擎进程带着
`SSL_CERT_FILE`（`EngineConfig.buildEnv`），所以 App 里的会话正常；终端里没有，
于是每个 https 请求都死在加载信任锚这一步 —— 报 `TRANSPORT: Connection error`，
看起来完全像"手机没网"。

`# kxxy-shell@7` 给交互式 shell 补 `SSL_CERT_FILE` / `CURL_CA_BUNDLE` /
`REQUESTS_CA_BUNDLE`（都只在文件存在、用户没设过时写）。

### 第二堵：headless profile 看不到「模型」页的选择

`dsh headless` 只挂 `dsh-base` + `dsh-headless` 两个 bundle，没有 web 的
`cordis.patch.yml`，于是模型选择掉回上游默认 `deepseek-official` —— 那条路由
只认 `DEEPSEEK_API_KEY`，而用户配的是硅基流动（`dhd`）。症状是
`MISSING_CREDENTIAL: … provider route "deepseek-official"`，像凭据丢了。

两件事：

1. `plugins/kxxy-host/lib/default-model.mjs` 新增 `mirrorSelectionToHeadless()`：
   把 web 补丁里的 `agent-default-model` 与 `llm-*` 条目（按顶层 `- ` 切块，原文照搬，
   不做 YAML 往返）镜像到 `profiles/headless/cordis.patch.yml`。只在目标是
   `[]`（出厂态）或首行是 `# [kxxy] …镜像…` 时接管；用户手写过的一律不动。
   引擎每次启动跑一次，内容一致不写盘。
2. `plugins/kxxy-host/lib/ghraw.mjs` 的助手目录多了一个 `dsh-headless`：
   它补 TLS 变量、把 `$DSH_HOME/.credentials.yaml` 的 `refs:` 段导出成环境变量
   （已设的不覆盖），然后 `exec dsh --profile headless "$@"`。不写文件、不改 profile。

### 验证（真机）

刻意不设 `SSL_CERT_FILE` / `DHD_API_KEY`，直接 `dsh-headless "只回复 OK"` →
输出 `OK`。`dsh-headless` 是插件启动时幂等写入的，`~/.kxxy/bin` 已在 PATH 上。

## 4. 未做：Android SDK 不完整（Gradle 打不了 Android 包）

现状：有 `aapt2` / `d8` / `apksigner` / `zipalign` / `bundletool` / `adb` /
`android.jar`，缺 `sdkmanager`、`platforms/`、`build-tools/`，`ANDROID_HOME` 未设，
`~/.gradle/wrapper/dists` 也没有。

可行路径（约 200–300 MB 下载）：

```
cmdline-tools (aarch64 无官方包，需 java -jar 运行 sdkmanager 的镜像版)
  → sdkmanager "platforms;android-35" "build-tools;35.0.0"
  → export ANDROID_HOME=<root>/android-sdk
```

没做的原因：它属于"扩展池"级别的一次性大件（跟 zig 当初进池同类），要单独
决定是打包进 runtime 还是首次使用时下载；而且 Gradle 构建还需要
`gradle/wrapper/dists` 的 wrapper 本体。这次只把结论记下来，没动。

## 5. 未改：npm / pnpm / yarn 三个源 + `package-import-method` 警告

- `npm_config_registry` / `NPM_CONFIG_REGISTRY` / `COREPACK_NPM_REGISTRY` 都是
  npmmirror（`EngineConfig.buildEnv`）；pnpm 默认 `registry.npmjs.org`，
  yarn 默认 `registry.yarnpkg.com`。三者不统一是**事实**，但不是故障。
- `RuntimeInstaller.ensureNpmrc…` 往 `~/.npmrc` 写 `package-import-method=copy`
  （为了让 pnpm 不去硬链 —— 应用域 link(2) 必 EACCES）。npm 读同一个文件，于是每次
  都警告 `Unknown env config "package-import-method"`，npm 12 会直接报错。

**没有直接改**的原因是：把这项挪到 pnpm 自己的全局 rc（`$XDG_CONFIG_HOME/pnpm/rc`）
才干净，但 pnpm 各版本对那个文件的读取行为不一致 —— 一旦某版不读，pnpm 就回到
`auto`（先 clone 再 hardlink），又会撞上应用域的硬链失败。要改必须先真机验证
pnpm 版本 + rc 路径，属于"改配置前先做 A/B"的活。`JAVA_TOOL_OPTIONS` 的
`Picked up …` 也是同一类噪音：它承担了 jansi 关闭与内存参数，撤掉换 `JAVA_OPTS`
会牵动 gradle/kotlinc 好几个调用点，收益只是日志干净，暂不动。

## 6. 不是故障：`profiles/web` 没有 node_modules

`dsh-web-mobile` 等实际装在 `engine/lib/node_modules`，Node 的解析规则会向上查找，
所以运行时完全正常；在 profile 目录里跑 `npm ls` 报的一堆 missing 是**假警报**。

真正的坑在以后：如果改用 `dsh plugin --profile web <pkg>` 安装，它会往
`profiles/web/node_modules` 落一份 —— 与现有"引擎顶层"布局并存，可能出现同名插件
两份、升级只升一份。要动这条，先统一插件安装位置。

## 7. 出包：v0.9.80（patchset @38）

上面的修复都在源码里，但真正会让已装设备变好的只有一件事：**让安装器重新解压**。
所以 `PATCHSET_MARKER` 从 `@37` 涨到 `@38`（`build-runtime.mjs`、`RuntimeInstaller.kt`、
`test-runtime-capability-contracts.mjs` 三处逐字一致）。

流程与产物：

| 步骤 | 结果 |
|---|---|
| runtime 构建 | 18m36s，76982 条目，`assets/runtime.zip` 982,445,371 B，sha256 `feebf487…` |
| glibc 池重建 | 只重打 `KXXY_POOL_ONLY=glibc`，写到 hold；provision 脚本 CRLF **163 → 0**（6835 B） |
| APK 构建 | 12m28s，`dist/Kxxy-0.9.80.apk` 2,856,585,246 B，`versionCode=980000` / `0.9.80` |
| 装机 | `adb install -r` 2m34s，首启按 @38 重解压 |

装机后的实测（Redmi K60 Pro / Android 13）：

- `patchset.version` = `kxxy-patchset@38`
- `python -V` → 3.14.8；`kxxy-py -V` → 3.12.3；numpy 2.5.4 / sklearn 1.9.1 / cv2 5.1.0 / pandas 3.1.1
- 首次使用自动预置：`dotnet 8.0.134`、`julia 1.11.7`、`wkhtmltopdf 0.12.6`
- `zig version` → 0.17.1（`bin/zig → ../lib/zig/zig`）
- `dsh-headless "只回复 OK"` → `OK`，headless 补丁带 `# [kxxy] 由 kxxy-host 从 web profile 镜像` 头
- 控制台 **11/11 项正常**，`GitHub 直链` 绿勾，明细是绕行说明；运行时完整性 9/9

### 一个容易漏的点：池不随 runtime 构建更新

`runtime.zip` 里**没有** `extensions/` —— 扩展由 `assets/ext-pool/*.pool` 单独注入。
第一次出包时 `glibc.pool` 还是 11-22 的旧版，里面的 provision 仍是 163 个 CR；
如果直接打 APK，这个 P1 会原样带上。所以出包顺序必须是：

```
重建受影响的池 → 构建 runtime → 构建 APK
```

判据也很直接：`tar -xOf glibc.pool bin/kxxy-glibc-provision | grep -c $'\r'` 必须是 0。
APK 打完后可以直接从成品里读同一个条目复核（本次 APK 内即 0）。

另注：本测试机的 `files/engine/extensions/` 早于修复就存在，安装 APK 不会覆盖它，
所以那台机器上的 zig 软链与 LF 脚本是排查期间就地修的结果，不是这次安装产生的；
**干净安装**才会从新池里取，池内容已按字节核过。
