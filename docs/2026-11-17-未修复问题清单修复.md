# 未修复问题清单（2026-11-17）四项处置

清单列了 4 项，但只有 **2 类根因**：第 2/3/4 项主要都是同一个 ICU 版本断层在三处载荷上的
投影；此外第 3、4 项在 ICU 修好之后又各暴露一个「编译期绝对路径钉在 Termux 前缀」的问题。
都不是「配置不对」，而是构建期决策在设备上的必然结果。

## 一句话结论

| 清单项 | 真根因 | 改法 |
| --- | --- | --- |
| 1. Maven 不可用 | `bin/mvn` 是 deb 里 `-> ../opt/maven/bin/mvn` 的**符号链接**，`poolextract.py` 把它物化成实体副本，脚本用 `dirname $0/..` 反推出的 `MAVEN_HOME` 于是落在 `extensions/maven` —— 那里没有 `boot/` | extinstall 把副本**换回相对软链**（缺陷 EJ） |
| 2. XeTeX / XeLaTeX 不可用 | 索引里 `libicu` 已推到 **79.1**，而 `texlive-bin` 仍是按 **78** 编译的；ICU 每个 major 重命名导出符号（`u_strlen_78`/`_79`），soname 指过去也解析不了 | 新增**兼容包**机制：同一个包的第二个 major 一起进运行时（`libicu` 78.3 与 79.1 并存） |
| 3. PHP 不可用 | ① 同上（`php`/`php-cgi`/`phpdbg` 链 `libicuio.so.78`）② `php-cgi`/`phpdbg` 的 opcache 锁目录编译期钉在 `$PREFIX/tmp` | ① 兼容包 ② `ensurePhpIni()` + `PHPRC` |
| 4. tesseract 训练功能不可用 | ① 同上（`libpango_training.so`/`libunicharset_training.so` 链 `libicuuc.so.78`）② 默认 datapath 钉在 `$PREFIX/share/tessdata` | ① 兼容包 ② `TESSDATA_PREFIX` |

## 1. Maven —— 物化副本让启动脚本认错了家

`Termux` 的 maven 包里，`usr/bin/mvn` 是一条指向 `usr/opt/maven/bin/mvn` 的符号链接。
`tools/lib/poolextract.py` 的 `materialize_links()` 会把包内链接**解析成实体文件**（这是
为了让 `tar.mjs` 不必处理 type '2' 目录项，历史上还因此产生过缺陷 BN/BR），于是扩展池里
`extensions/maven/bin/mvn` 是一份**真副本**。Apache 的启动脚本这样定位自己：

```sh
PRG="$0"                                  # 已被 <-h> 循环解析到 extensions/maven/bin/mvn
MAVEN_HOME=`dirname "$PRG"`/..            # → extensions/maven
CLASSWORLDS_JAR=`echo "${MAVEN_HOME}"/boot/plexus-classworlds-*.jar`
...
-classpath "$CLASSWORLDS_JAR"
```

`extensions/maven/` 下只有 `bin/ lib/ opt/`，`boot/` 在 `opt/maven/` 里头 —— 通配符
匹配不到任何东西，**字面量 `*.jar` 原样进了 `-classpath`**，于是：

```
Error: Could not find or load main class org.codehaus.plexus.classworlds.launcher.Launcher
```

### 为什么 v0.9.62 的「PATH 前置 opt/<name>/bin」没兜住

`EngineConfig.kt` 早就把 `<root>/opt/{maven,gradle,kotlin}/bin` 排在 `<root>/bin` 之前
（缺陷 BN），真机 A/B 也确认那条路是通的。但它只在**三个条件同时成立**时有效：

1. `opt/` 视图已经被 `mergeViews` 摊出来（`<root>/opt/maven -> extensions/maven/opt/maven`）；
2. 调用方用的就是我们那份 PATH；
3. 扩展装完之后视图合并**已经跑过**。

`<root>/bin/mvn` 这条链接链、用户自己拼的 PATH、以及「池刚展开、视图还没合并」的窗口期，
都会命中副本。本清单报的就是这几种情况之一。

### 改法：把副本换回软链（缺陷 EJ）

`plugins/kxxy-host/lib/extinstall.mjs` 新增 `relinkShadowedLauncher()`：

- 只处理 `<ext>/bin/<name>` 与 `<ext>/opt/<pkg>/bin/<name>` **同名同大小**的普通文件，
  4 MiB 以下再比一遍内容 —— 同名同大小但内容不同，说明它们本来就不是一份；
- 换成**相对**软链 `../opt/<pkg>/bin/<name>`（相对目标随扩展目录一起搬，不会因
  `filesDir` 变化失效；Apache 脚本的 `[ -h ]` 循环能正确解析相对目标）；
- 建链失败立刻把内容写回并恢复权限，不留下一个空命令。

接线两处：

- `buildViews()` —— 安装扩展时，在 `collectBins` 之前先换链，这样 `<root>/bin/mvn`
  这条链的第二跳就直通真身；
- `healBinEntry()` —— 启动自愈（`healExtensions`）里对**已装**扩展做同一件事，
  所以不需要用户重装 maven（扩展是用户资产，重装要重新解 9 MiB 包池）。

同一形状的 gradle / kotlin 顺带修好（它们缺的是 `lib/`，只是 PATH 前置恰好盖住了）。

## 2–4. ICU 78 / 79 断层

### 现场

```
$ php -v
CANNOT LINK EXECUTABLE "php": library "libicuio.so.78" not found: needed by main executable

$ xelatex --version
CANNOT LINK EXECUTABLE "xelatex": library "libicuuc.so.78" not found: needed by main executable
```

引擎根 `lib/` 里只有 `libicu*.so.79.1`。扫一遍运行时确认过：**除了 ICU 自己，
全树只有 `bundled` 的那几个负载要 78，而 `bin/node` 要 79**：

| 消费者 | 需要 |
| --- | --- |
| `bin/node`（`nodejs-lts`，引擎本体） | `libicuuc.so.79` |
| `bin/php` `php-cgi` `phpdbg` | `libicuio.so.78` + `libicuuc.so.78` |
| `bin/xetex` `xelatex` `bibtexu` `upmendex` | `libicuuc.so.78` |
| `lib/libharfbuzz-icu.so`、tesseract 的两个 `*_training.so` | `libicuuc.so.78` |

### 为什么不能只留一个 major

- **不能钉回 78**：`nodejs-lts` 是按 79 编的，钉回 78 会让引擎本身启动失败；
- **不能把 soname 指过去**：ICU 把版本号编进符号名（`u_strlen_78` / `u_strlen_79`），
  `ln -s libicuuc.so.79.1 libicuuc.so.78` 只会在第一次符号解析时就报
  `undefined symbol: u_strlen_78`。真机核对过：`libicuuc.so.79.1` 里 `_78` 后缀 0 命中、
  `_79` 1 命中；
- **不能等上游重编**：索引里那批包（`php 8.5.12-1`、`texlive-bin 2026.0-2`、
  `tesseract 5.5.3`）今天就是 78 链接的，`libicu` 已经到 79.1 —— 这是 Termux  rebuild
  窗口期的常态，不是我们能用参数绕开的。

所以只能让**两代 major 的文件同时存在**。代价：`libicu_78.3` 的 deb 10.2 MiB
（解开 44 MiB，几乎全是 `libicudata`）。

### 改法：兼容包（`SEED_COMPAT_PACKAGES`）

`tools/lib/seeds.mjs` 新增：

```js
export const SEED_COMPAT_PACKAGES = [
  { name: "libicu", version: "78.3",
    why: "php / xetex / tesseract 训练库按 ICU 78 链接，nodejs-lts 需要 ICU 79" },
];
```

`tools/fetch-runtime.mjs` 在闭包下载完之后，把缓存里的该版本 deb 作为**额外包**写进
`.cache/debs/manifest.json`，并且 **`unshift` 到 `packages` 最前面**。顺序有语义：
`debextract.py` 按 `packages` 顺序解、**同名路径后者覆盖**，兼容包排前面才能保证

- `lib/libicuuc.so` 这类**不带版本号**的开发链接仍指向 79.1；
- `include/unicode/*` 头文件仍是 79 那份；
- 兼容包只净增 `libicu*.so.78` + `.so.78.3` 两族文件。

与 `SEED_VERSION_PINS` 的区别写在注释里：pin 是「换成老版本」，兼容包是「新旧都要」。

### 链接通了之后的第二层：两处编译期绝对路径

ICU 两代并存解决了「加载器找不到库」，但 `php -v` 能跑之后，`php-cgi` 与 `tesseract`
各自又暴露出一个**编译期常量**问题。这类路径在打包时就写死成 `$PREFIX`（Termux 的
`/data/data/com.termux/files/usr`），`libkxxy_exec.so` 的路径重写对它们的覆盖并不完整。

| 症状 | 常量 | 改法 |
| --- | --- | --- |
| `php-cgi -v` → `Fatal Error Unable to create opcache lock file in /data/data/com.termux/files/usr/tmp` | `opcache.lockfile_path`（编译期 `$PREFIX/tmp`） | 生成 `<root>/etc/php/php.ini` 重定向 |
| `tesseract --list-langs` → `Error opening data file …/com.termux/files/usr/share/tessdata/` | `TESSDATA_PREFIX`（编译期 `$PREFIX/share/tessdata`） | `EngineConfig` 注入 `TESSDATA_PREFIX=<root>/share/tessdata` |

`plugins/kxxy-host/lib/extinstall.mjs` 新增 `ensurePhpIni(root)`：在 `<root>/etc/php/php.ini`
里写三条 —— `opcache.lockfile_path`、`sys_temp_dir`、`upload_tmp_dir`，全部指向
**按设备现算**的 tmp（`process.env.TMPDIR || TMP`），不写占位符；幂等（内容一致不重写）；
`<root>/bin/php` 不存在时直接返回 `{written:false}`，不会给没装 php 的设备凭空建目录。
`index.js` 的 `runHeal()` 里调用它，写成功计一次 `repaired`。

**为什么写 ini 而不是只造一个 `$PREFIX/tmp`**：那个前缀在设备上根本不存在，而 opcache
要的是可写的锁目录；把它重定向到 App 自己的 tmp 才能顺带解决 `sys_temp_dir`、
`upload_tmp_dir` 两个同源默认值（都指向 `$PREFIX/tmp`）。

关于 `PHPRC` 的定位需要说清楚 —— 实测结论与最初判断**不同**：

| 实验 | 结果 |
| --- | --- |
| 有 ini、无 `PHPRC` | `php-cgi -v` 正常 |
| **删掉 ini**、无 `PHPRC` | 复现原始 `Fatal Error Unable to create opcache lock file` |
| 删掉 ini、`PHPRC=/system`（空目录） | 仍然 Fatal ⇒ 起作用的不是「设了 PHPRC」，而是 ini 的内容 |
| 有 ini、`LD_PRELOAD=` 全空、带 `PHPRC` | 正常 |
| 有 ini、`LD_PRELOAD=` 全空、无 `PHPRC` | 仍然 Fatal |

也就是说：**根因修复是 ini 文件本身**；`PHPRC` 是一条**不依赖 preload 的显式寻址**。
没有 preload 时，PHP 会回到编译期路径 `$PREFIX/etc/php/php.ini` 去找 ini，而
`libkxxy_exec.so` 的路径重写在有 preload 时能把这次 open 重写到 `<root>/etc/php/`，
去掉 preload 就断了 —— `PHPRC` 直接指真地址，不依赖任何重写。实测去掉 `PHPRC` 时
`php --ini` 报的仍是 Termux 路径（`Loaded Configuration File: "/data/data/com.termux/files/usr/etc/php/php.ini"`），
这正是「靠重写才找到」的证据。

`PHP_INI_SCAN_DIR` 不能替代它：那个变量只决定 `conf.d` 的扫描目录（`php --ini` 里单独一行
`Scan for additional .ini files in`），改不动主 ini 的搜索路径。

真机确认（`php-cgi -i` 摘录）：

```
Loaded Configuration File </td><td class="v">/data/user/0/app.kxxy/files/engine/etc/php/php.ini
opcache.lockfile_path</td><td class="v">/data/user/0/app.kxxy/files/tmp
sys_temp_dir</td><td class="v">/data/user/0/app.kxxy/files/tmp
```
