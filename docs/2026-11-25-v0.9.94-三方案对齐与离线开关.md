# v0.9.94：三方案对齐（图片模态 / Office 后端 / glibc 离线）

对应用户给的三条修复方案。本文记录**采纳了什么、没采纳什么、为什么**，以及可以复现的判据。
口径：所有结论都取自本仓库真实产物（`.cache/.rc3-res/resources/app.asar` 与 `.cache/app.asar`），
不是上游文档推断。

| 问题 | 方案建议 | 实际做法 | 差异 |
|---|---|---|---|
| ① 图片被拒 | 方案 B：未声明且目录查不到 → 对外**不输出** `inputModalities` | 保留按协议补 `image`（0.9.93 已做），补钉三条判定语义 | 本产物有**第二道门**，只置空 `inputModalities` 会在请求期失败，见下 |
| ② Office 原生 | 先 P2-A（显式化后端） | 能力探针新增 `office_engine`，跑 Kit 自己的 `capabilities --json` | 没动 office-kit 结果结构与前端；P2-B/C 不做 |
| ③ glibc 工具 | P3-A 联网 / P3-B 离线 | P3-B 已在 0.9.93 交付；本次补 `KXXY_GLIBC_OFFLINE=1` 与已装快路径 | 一致，另加严格离线开关 |

## ① 图片模态：为什么不能只「不输出 inputModalities」

方案里的取值链诊断是对的，但漏了准入之后的第二道判定。本产物里图片有**两道**门：

1. **准入**（`dsh-api-session-controller`，`commands.ts:353` 编译后为
   `lib/index.js:921`）：

   ```js
   if (model.inputModalities !== void 0 && !model.inputModalities.includes("image"))
     throw new RemoteError("session/attachment-invalid", `Model "${current.model}" does not support image input.`, ...)
   ```

   这里 `undefined` 确实放行 —— 方案 B 在这一步成立。

2. **请求期**（`dsh-llm-pi-ai/lib/index.js:2244`，`streamWithSnapshot` 内，无任何可选链）：

   ```js
   const containsImage = options.messages.some((m) => contentHasImage(m.content));
   if (containsImage && !model.input.includes("image"))
     throw new LlmError(`pi-ai model "${model.id}" does not support image input`, "UNSUPPORTED_CONTENT");
   ```

   `model` 是 pi-ai 解析后的模型条目，`input` 仍由 schema 默认成 `["text"]`。
   所以「只把 `inputModalities` 置空」的结果是：准入放行 → 这里抛
   `UNSUPPORTED_CONTENT`，用户看到的是另一句错误，图仍然发不出去。

`tools/test-model-modality-fallback.mjs` 现在钉住了这道门（少了它就说明上游放宽了判定，
届时可以退回只报 modality）：

```js
assert.ok(original.includes('if (containsImage && !model.input.includes("image")) throw new LlmError('), ...)
```

另外两个消费方也依赖「声明了 image」才肯用图：`dsh-acp/lib/index.js:84`
（`inputModalities?.includes("image") === true`）与 `dsh-cua/lib/index.js:1845`。
把 `inputModalities` 置空会让 ACP 客户端与 CUA 截图把能力报成 false，
而这两条路由的图其实发得出去 —— 那才是「谎报」，方向相反。

### 现在实现的行为

`unknownRouteInput(api, id, defaultInput)`（补丁集 `@42`）：

- 目录（`base`）与目录回退（`modalityBase`）都落空时，按 wire 协议判定：
  `openai-completions` / `openai-responses` / `anthropic-messages` /
  `google-generative-ai` → `["text", "image"]`；
- 目录**明确**写纯文本的（`deepseek-v4-pro` / `o3-mini` / embedding）由
  `knownTextOnlyModel()` 拦住，兜底不得放行；
- 非对话协议、`api` 缺失 → 原样返回 `defaultInput`；
- `KXXY_MODALITY_UNKNOWN=strict` 整体退回「未知即纯文本」。

### 三条判定语义逐条回归

`tools/test-model-modality-fallback.mjs` 新增了顺序断言（不再只比对整串）：

```
declaredInput(entry.input) → request.defaultInputDeclared === true → base?.input
→ modalityBase?.input → unknownRouteInput(...)
```

对应方案里的三条：① 声明了按声明；② 未声明且目录/回退都没有 → 不再落到 schema 的
`["text"]`（本产物里是「按协议补 image」而非 `undefined`，原因见上）；③ 显式
`defaultInput` 优先于 `base`。

## ② Office：后端显式化（P2-A）只做了「可查」这一半

**没做的**：office-kit 转换结果里加 `engine`、前端显示「WASM 渲染」。
理由：`dsh-office-kit` 的返回值被 `dsh-tool-office` 直接喂给前端（`lib/index.js` 里
没有 engine 字段），改结构要同时改前端 bundle，而前端是打包后的 web 资源、无法在
无真机条件下验收；把 WASM 硬写进 `dsh-skill-office` 的 SKILL.md 又是给共享文档写平台事实，
换平台就错。

**做了的**：`tools/probe-runtime-capabilities.py` 新增 `office_engine` 检查，直接跑
Kit 自己的命令，而不是我另写一份 import：

```bash
node <engine>/lib/node_modules/@deepseek-ai/libreoffice-kit/lib/cli.js capabilities --json
# → {"runtime":{"version":"0.2.3","backend":"wasm","nativePreview":false,...},
#    "conversions":[...],"imageRendering":{"pdfBackend":"pdfium",...}}
```

探针把它整理成：

```json
{"status": "pass", "kitVersion": "0.2.3", "backend": "wasm", "native": false,
 "nativePreview": false, "pdfBackend": "pdfium",
 "note": "WASM engine: conversion works, desktop-exact layout is not guaranteed"}
```

要点：

- **不进必检项**（`required` 列表没动），office 缺失只报 `skip`，不会把整份报告判失败；
- `backend` / `native` 直接给出结论，`note` 是给人看的一句话；
- 本机实跑验证过三条分支（wasm / native / 无 JSON → skip），桩输出那段在
  `docs` 里不重复贴。

**P2-B（真原生 + proot 桥）不做的原因**（保持 0.9.93 的判断，补充事实）：

1. 设备上没有 `@deepseek-ai/libreoffice-kit-linux-arm64-glibc` 这个 optional 包，
   `ENGINE_VERSIONS` 里有 `linux-arm64-glibc: 0.1.1` 也只是「上游发布过」，没随本轮装；
2. `platformTarget()` 在 bionic 上返回 `undefined` 是**架构判定**，不是配置缺失：
   原生引擎要 dlopen 一个 glibc 链接的 `libsofficeapp.so`，进程内做不到；
   P2-B 的实质是「把 soffice 子进程塞进 proot」，而 Kit 现在走的是进程内 Node API
   （UNIX socket / 子进程回连），换后端等于重写调用层；
3. 中文排版还依赖 `systemFontDirectories()` 追加 rootfs 字体，这条没在真机上验过。

**P2-C（外挂 soffice）** 同理：需要容器常驻 + 新的 `engine: 'external'` 配置面，
收益（排版保真）与代价（启动 5–10 s、容器状态耦合）不成比例，不做。

## ③ glibc 工具：P3-B 已在 0.9.93，本轮补严格离线

0.9.93 已把三份离线包随扩展发布（`extensions/glibc/provision/`：
julia 285 MiB、dotnet SDK 199 MiB、wkhtmltopdf 闭包 91 MiB），本地包优先。
本轮补的是方案 P3-B 的第 2 条与两条快路径：

1. **`KXXY_GLIBC_OFFLINE=1` 禁止一切联网**。缺本地包时直接报

   ```
   kxxy-glibc-provision: KXXY_GLIBC_OFFLINE=1，但 Julia（离线包已缺失）需要联网
     → 离线模式只走随扩展的本地包（julia / dotnet / wkhtmltopdf 三个）。
     → python-ml / python-data / python-torch 需要网络；
       想离线用 Python 请直接用原生 python3（已自带 numpy/scipy/pandas/torch）。
   ```

   覆盖点：`prov_base`（apt）、`prov_python`（pip）、三个工具的 tarball 回退。
   不再出现「弱网下静默拉 285 MiB、看起来像卡死」。

2. **已装快路径前移**。原来 julia 先看离线包、再看是否已装 —— 标记丢了会把 285 MiB
   重解一遍；现在三个目标都是「stamp → 容器里 `--version`/`-x` 探一次 → 本地包 → 联网」。
   `prov_python` 的 `import sklearn, cv2` 检查也从 `apt install python3-pip` 之后
   提到了最前面（离线模式下不再因为 apt 被拦而误判 Python 不可用）。

3. 扩展版本 `24.04.3-r4 → r5`（池内容变了，装过的人要重装一次；rootfs 不受影响）。
   设备侧的自动重装判据是 `.links.json` 里的 `poolBytes` 与当前池体积比对
   （`staleExtensions()`），所以即使版本号没变也会触发；版本号只是给人看。

## 复现与验收

```bash
# ① 判定链（两份 asar 各跑一遍，含第二道门断言）
node tools/test-model-modality-fallback.mjs
# → RESULT {"asars":2,"checks":8,"passed":8,"failed":0}

# 运行时契约（补丁集标记、必需条目）
node tools/test-runtime-capability-contracts.mjs

# ② 设备上确认 Office 后端（把探针拷到设备后，用引擎原生解释器跑）
$KXXY_ENGINE_ROOT/bin/python -I probe-runtime-capabilities.py \
  --root "$KXXY_ENGINE_ROOT" --scratch-parent <可写目录>
# → checks.office_engine.backend == "wasm"

# ③ 离线预置（飞行模式）
kxxy-glibc-provision julia dotnet wkhtmltopdf          # 走随扩展的本地包
KXXY_GLIBC_OFFLINE=1 kxxy-glibc-provision python-ml    # 应明确报「需要联网」
```
