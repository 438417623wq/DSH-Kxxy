# 客户端插件兼容与「不兼容也不白屏」

> 2026-11-02 · 对应版本 0.9.9 / 补丁集 `kxxy-patchset@10`

## 症状

用户在控制台「插件」页停用了 `@neystan/dsh-web-ui-all`（task-board / pet /
describe-image 三件套）与 `dsh-at-file`，重启引擎后对话页**整页**只剩：

```
HARNESS
Failed to load plugins

@neystan/dsh-client-ui-task-board
@neystan/dsh-pet
@neystan/dsh-tool-describe-image

web boot: 3 entries did not activate
@neystan/dsh-client-ui-task-board: import failed: client-modules:
require('@deepseek-ai/dsh-client-runtime/client') missed the module table -
not a platform seed word, not a materialized module, and no registered
package factory (a build-time externals drift, or a dynamic dependency
that did not arrive)
```

同一句错误出现 4 次（每个插件一次）。引擎活着、会话完好、控制台进得去，
只有对话页是白底错误页 —— 与 10-31 那次「体检全绿但进不去」是同一个病灶。

## 根因（两个，叠在一起）

### ① 上游把「客户端运行时总包」拆了，老插件还在按老名字 import

`@deepseek-ai/dsh-client-runtime` 是 0.1.x 时代的**客户端运行时总包**，插件在
全盛期都依赖它。当前 0.2.1-rc.5 把这套东西拆成了 `dsh-client-store` 加一票
`dsh-client-ui-*`，总包本身**不在安装树里**（`app.asar` 18234 个条目里一条都
搜不到）。

而这些插件的客户端 bundle 里有一行 `require("@deepseek-ai/dsh-client-runtime/client")`。
前端模块加载器（`dsh-client-modules`）的解析顺序是：

```
seed word（平台种子）→ 已物化模块 → 图里的行 → 已注册的工厂 → 抛错
```

四个分支全不命中，于是抛出上面那条「missed the module table」。报错里特意写了
原因：`a build-time externals drift` —— 插件在构建时把某个包当外部依赖，而
运行时那边**这个名字不认识**了。

### ② 前端 boot 的「汇总诊断」拥有杀页面的权力

`dist/assets/index-<hash>.js` 里的 boot 收尾（`IZ`）会遍历所有 entry 的最终状态，
**只要有一条不是 `active` 就 `throw`**，上层 `catch` 里直接 `page.fail(...)`
把整页换成错误卡。

问题在于：`IZ` 只是**汇报**。它跑之前，loader 已经把每个 entry 的失败隔离在
自己的 fiber 里了；紧随其后的挂载（注入 `uiRenderer`）完全可能正常。也就是说，
一个第三方插件的 import 失败，能连坐掉整个对话页。

用户的原话是「哪怕不兼容也不应该崩溃」。

## 修法

### ① 别名：老名字指向同一个 store 种子

打在 `dsh-client-modules/lib/client.js` 的种子表构造点：

```js
this.seed = new Map(Object.entries(options.staticModules));
/* KXXY_CLIENT_RUNTIME_ALIAS: … */
for (const [kxxyAlias, kxxyTarget] of [["@deepseek-ai/dsh-client-runtime/client", "@deepseek-ai/dsh-client-store"]]) {
  if (!this.seed.has(kxxyAlias) && this.seed.has(kxxyTarget)) this.seed.set(kxxyAlias, this.seed.get(kxxyTarget));
}
```

**为什么这是等价而不是将就**：下载了 `@deepseek-ai/dsh-client-runtime@0.1.1-rc.2`
对着看 —— 它的 `lib/types/client/contract/store.d.ts` 里，`./client` 子路径干的
唯一一件事就是转出 store 契约（`createSnapshotStore` / `defineStore` /
`shallowEqual`），与当前前端产物里的 store 实现函数名、参数、返回值一致。

再核对这批插件**实际用到**的成员（扫客户端 bundle 的 `require` 结果引用）：

| 插件 | 用到的成员 |
|---|---|
| `@neystan/dsh-client-ui-task-board` | `createSnapshotStore` |
| `@neystan/dsh-tool-describe-image` | `createSnapshotStore` |
| `dsh-at-file` | `createSnapshotStore` |
| `@neystan/dsh-pet` | `createSnapshotStore` / `defineStore` |

所以把老名字指到同一个对象上，语义完全对齐。

**为什么打在加载器而不是前端产物**：种子表在前端 `dist/assets/index-<hash>.js`
里，文件名带内容哈希、每次发版重新压缩；而种子表是**前端传进来的参数**，
加载器是普通打包产物 —— 路径稳定、代码可读。补在加载器里，前端换版不用跟着改。

只补 `/client` 这一个子路径。裸包名不补：插件对它的期待是整个运行时 API，
拿 store 顶上会在别处变成 `undefined is not a function`，比一条明确的 import
失败更难查。

### ② 降级：第三方插件失败只跳过，官方包仍然硬失败

同一份前端产物里，把 `IZ` 结尾的 `throw` 换成按来源分档：

```js
const kxxyFatal = r.filter((line) => /^@deepseek-ai\//.test(line));
if (kxxyFatal.length > 0) throw new Error("web boot: … did not activate\n" + …);
if (r.length > 0) console.warn("web boot: … from third-party plugins failed and were skipped …\n" + …);
```

- **官方包（`@deepseek-ai/*`）失败 → 仍然硬失败**。它们与运行时是同一套安装，
  集体失败意味着运行时本身坏了，这时候一张能读的错误卡比半残界面有用。
- **其它（第三方 / 自带插件）→ 只告警并继续挂载**。页面照常可用，坏掉的那个
  插件就是「它的功能不出现」。

不吞信息：`IZ` 只是汇总，真正的致命问题会在紧接着的 `uiRenderer` 注入/挂载
那一步抛出来，仍然走原来的 `page.fail`。

## 配套改动（不做这些，前两条会以另一种方式骗人）

| 位置 | 改什么 | 为什么 |
|---|---|---|
| `tools/build-runtime.mjs` / `RuntimeInstaller.kt` | 补丁集 `@9` → `@10` | 这两条补丁改的是**运行时里已有文件的内容**；设备端的 `isComplete()` 只看锚点与标记文件，不递增的话装完新 APK 仍跑旧文件，现象是「更新了但插件还是白屏」 |
| `WebBootLog.kt` | 特征串加 `failed and were skipped` | 降级后的告警也值得落盘，否则体检对「有个插件没生效」完全无感 |
| `health.mjs` | 浏览器侧记录分两档：硬失败 BAD / 已跳过 WARN | 「页面进不去」和「页面能用但少个面板」不能共用一档，否则要么吓人要么掩盖白屏 |
| `plugins.mjs` | 失败原因也取浏览器侧消息；聚合包按依赖判定；新增 `soft` 标记 | 引擎日志只知道「没激活」，真正的根因（`missed the module table`）只有前端 console 有；聚合包自己不上前，子插件挂了它不红的话，用户会以为「插件页一切正常」 |
| `web/host.js` | 告警条文案分两档 | 「已自动跳过，页面照常可用」与「会让对话页停在 Failed to load plugins」是两件事，混用会把人吓一跳 |
| `verify-runtime.mjs` | 新增两组补丁痕迹检查 | 标记文件在 ≠ 补丁内容在。真机事故就是这么发生的 |

## 验证

- `node tools/test-client-compat.mjs` —— **24 项**：别名插入位置/指向/语法、
  两条补丁的幂等、降级后的判定语义（第三方只告警、官方仍抛错、混合失败时
  官方那一档仍致命）、改完的前端 chunk 通过 `node --check`。
- `node tools/test-bootreport.mjs` —— **43 项**（新增 8 项）：已跳过 → WARN 而非
  BAD、WARN 里点出包名、文案说明页面可用、失败原因取自浏览器消息、聚合包因
  子插件失败而红并借到原因。
- 回归：`test-guard` 21、`test-extinstall` 101、`check-bundle`、`smoke-plugin`
  全绿；`verify-runtime` 的补丁痕迹三项（归档/别名/降级）齐备。
- `verify-runtime` 断言 `KXXY_CLIENT_RUNTIME_ALIAS` 与 `failed and were skipped`
  真的落在 zip 里的文件上。

写测试时踩到一个坑值得记：上游压缩产物里那条 `did not activate` 的模板字符串
**直接断了一行**（真换行），不是 `\n` 两个字符。第一版正则写成 `\\n`，静默失配，
被这组测试当场抓出来 —— 也正因为它是「失配即无补丁」，这里用的是硬失败。

## 边界（说清楚，别当成万能）

- 别名只覆盖 `@deepseek-ai/dsh-client-runtime/client` 这一个已消失的包名。
  将来若有插件依赖别的**已删除**包，仍然会失败 —— 但不会再白屏，会被跳过、
  在插件页标红并给出原因。
- 插件若依赖的是「还在、但 API 变了」的包（例如某个 slot 名字改了），失败会
  发生在它的 `apply()` 里，同样按第三方 → 跳过处理。功能不出现，页面照常。
- 官方包失败仍然是白屏。这是刻意的：那种情况下继续挂载只会得到半残界面，
  而错误卡上的包名是唯一能定位问题的线索。
