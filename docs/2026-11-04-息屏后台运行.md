# 息屏后任务停住：CPU 挂起与唤醒锁

> 2026-11-04 · 对应版本 0.9.11
> 现场：会话正在执行任务、正常调用模型；**手机锁屏后进程没死、会话也没断，
> 但模型调用不再发出**，解锁回到前台后又接着跑。
> 用户原话：「我是看模型调用看出来的，已经不调用了」。

## 一、为什么「前台服务」没挡住

这套宿主原本只有一层保活：`EngineService`（`foregroundServiceType="specialUse"`，
无 Android 14 的 6 小时限时）。它解决的是**进程级**问题：

- 不被判为 cached 后被 Cached App Freezer 冻结；
- 不被 LMK 在内存紧张时优先回收；
- 不受 App Standby 分桶限制。

但它**完全不解决 CPU 级问题**。屏幕一灭、且没有别的应用持唤醒锁，内核几秒内
进入 suspend-to-idle：

```
dumpsys power | grep -i "mWakefulness="
  mWakefulness=Asleep          ← 屏幕灭
  mHoldingWakeLockSuspendBlocker=false
```

此时所有线程停在原地。Node 的事件循环不再转，正在飞的 HTTPS 请求既不超时也不
完成 —— 所以现象是「不报错、不中断、也不继续」。回到前台时内核被点亮，事件循环
从断点继续，看起来就是「一解锁就接着跑」。

清单里其实**一直有** `android.permission.WAKE_LOCK`，但全项目没有一行代码去取
它。这不是保活强度不够，是根本没有人叫醒过 CPU。

```
$ grep -rn "WakeLock" android/app/src/main/java   # 修复前：零命中
```

## 二、修复：`service/KeepAwake.kt`

三条约束，缺一条都会退化成另一个问题：

### 1. 只在息屏时持锁

亮屏时屏幕本身就在阻止 suspend，再持 `PARTIAL_WAKE_LOCK` 纯属浪费电。判断依据是
`PowerManager.isInteractive` + 动态注册的 `ACTION_SCREEN_ON/OFF`（这两条在
Android 8+ 的后台广播白名单里，动态注册可靠）。

### 2. 闲置 10 分钟自动让位（并且能自己回来）

整夜持锁会让待机从 ~1%/h 涨到 ~2–3%/h。所以每 20 秒读一次**引擎进程树的
CPU 时间**（`utime + stime + cutime + cstime`，直接子进程用
`/proc/<pid>/task/<pid>/children` 枚举，读不到再退化成扫 `/proc` 比 ppid）：

```
delta ≥ 8 jiffies（≈80ms / 20s）  → 视为「在干活」，刷新活跃时间
连续 10 分钟无 delta              → 放锁让位（idleRelaxed = true）
```

连子进程一起算是有意为之：`bash`/`node`/`python` 这类工具执行是引擎 spawn 出去
的子进程，一次 20 分钟的编译里引擎自己的 CPU 可能接近 0 —— 只看引擎 pid 会把
最不能被打断的场景误判成闲置。

让位后采样协程**不退出**，只是不持锁，靠 `delay` 挂起、不占定时器。设备 suspend
期间它自然不跑，被任意网络包/闹钟唤醒后继续采样 —— 于是新任务能自己把锁要回来。
这是「让位」不需要配闹钟的原因。

### 3. 不改前台服务语义

只加一把 CPU 锁：不引入第二套保活、不申请新的危险权限。锁在进程死亡时由系统
自动回收，不会出现「锁泄漏把电池吸干」的最坏情况。

持锁/放锁都在同一把监视器里做 —— 广播（主线程）、状态协程、采样协程会同时走到
那里，而 `setReferenceCounted(false)` 下的并发 `release()` 会撞出
`WakeLock under-locked`。

## 三、配套的三件事

| 位置 | 改动 | 为什么 |
|---|---|---|
| `MainActivity.setupWebView` | `setRendererPriorityPolicy(RENDERER_PRIORITY_IMPORTANT, false)` | 渲染进程默认按可见性降级，后台被回收后前端与引擎的流式连接断掉，界面上停在最后一条消息 |
| `EngineService` | 通知文案 `引擎已就绪 · 息屏运行中` | 锁屏上唯一能确认「它还在跑」的地方 |
| 设置页 | 「息屏继续运行」开关 + 实时状态 | 状态来自原生 `/proc` 采样，不是前端猜的 |

开关**默认开**：修复上线即生效，用户不需要先去某个角落点一下。关掉即恢复旧的
「锁屏挂起」行为。

## 四、与 Doze 的边界（必须说清）

Android 的 Doze（深度休眠）里**系统会无视唤醒锁**，并且掐断应用的网络。息屏静止
半小时以上就会进入 —— 也就是说，本修复解决的是「短时间息屏」，整夜在线仍然需要
把应用加入**电池优化白名单**：

```
adb shell dumpsys deviceidle whitelist | grep kxxy
```

所以打开开关时会顺手拉起 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`；未加入时
设置页会显示一行「电池优化白名单未加入」+「去设置」。这一行不是可选项，它是
「整夜跑任务」与「半小时后必然停」的分界线。

## 五、验收

真机上按这个顺序验，每一步都能独立证伪：

1. **持锁**：锁屏后 10 秒内
   `adb shell dumpsys power | grep -A2 "kxxy:engine"` 应有
   `PARTIAL_WAKE_LOCK 'kxxy:engine' ACQ`。
2. **不挂起**：`adb shell dumpsys power | grep mWakefulness` 仍是 `Awake`。
3. **任务继续**：锁屏后让 Agent 跑一个多步任务（含一次 `sleep 120` 的工具调用），
   解锁后时间线应当连续，没有「整段缺失」。
4. **让位**：锁屏静置 11 分钟（不跑任务）后，`dumpsys power` 里应看不到该锁，
   `dumpsys deviceidle` 能正常进入 idle。
5. **自愈**：让位之后（仍锁屏）通过 `adb shell am broadcast`/通知/定时任务触发一次
   运行，20 秒内应重新出现 ACQ。
6. **开关生效**：设置页关掉开关 → 锁屏 → 不出现 ACQ；再打开 → 出现。

自动化部分见 `tools/test-keepawake.mjs`（52 项，钉的是接线与字段契约）。

## 六、刻意没做的事

- **WifiLock**：`WIFI_MODE_FULL_HIGH_PERF` 要多吃一条 `CHANGE_WIFI_STATE`，且
  在 Doze 里同样被忽略。CPU 唤醒 + 长连接本身就能维持 Wi-Fi 关联，收益不值这个
  权限。
- **给 WebView 常驻前台**（如 `startActivity` 保活、静音音频）：属于灰产式保活，
  与「只加一把锁」的取舍冲突。
- **把开关做成三态**（始终持锁 / 息屏持锁 / 关闭）：多一档就多一个用户理解不了
  的状态，而「始终持锁」在亮屏时没有任何收益。
