# v0.9.86：中断轮次不再丢上下文、硅基流动工具调用兼容、手机附件与图片多模态

日期：2026-11-24　产物：`dist/Kxxy-0.9.86.apk`　versionName `0.9.86` / versionCode `986000`

这一版处理 Codex 侧栏上三个用户能直接撞到的问题，并把手机端附件链路补齐到「选了就能发」：

1. **同一个对话读不到上一条记录** —— 上一轮被停止或失败后，整轮历史被丢弃，下一条「继续」模型只看到两个字；
2. **硅基流动调用工具报「模型工具调用格式不对」** —— 流式分片里的 `null` 字段、重复 `name`、缺 `index` 全被当成协议错误；
3. **手机上加不了文件、看不到图** —— `+` 菜单只能引用工作区内 128 KiB 文本，运行中还整体锁死。

顺带把自定义模型的**图片多模态**接上：图片按三种协议分别编码成 `image_url` / `image` /
`input_image`，同时落盘到工作区，历史回放只保留路径说明。

本次还一并收拢了 v0.9.81–v0.9.85 遗留在工作区、尚未入库的改动（引擎配置与运行时安装、
glibc 启动器路线资产、java 壳绝对路径、容器 `/dev/shm` 等）。

## 1. 中断轮次的历史被整轮丢弃

`conversationMessages()` 原来有一句 `if (turn.status !== 'completed') continue`。
看起来是「只回放干净的历史」，实际后果是：一轮任务跑到一半被停止（`interrupted`）
或报错（`failed`），下一轮用户说「继续」，模型收到的上下文里**你的原始需求、已经执行
的命令、21 行输出、已生成的部分回复全部消失**，只剩孤立的「继续」。

修改分三层：

- `turnMessages()` 按状态区别对待：`completed` 原样回放；`interrupted` / `failed` 保留
  可用上下文；仍然只排除 `inProgress`（进行中的轮次不能被下一轮重复提交）。
- **悬挂工具调用补齐配对**：如果中断恰好停在模型刚发出 `tool_calls`、工具还没执行的位置，
  直接回放会让三种上游协议都因为缺少 `role: 'tool'` 而 400。回放层自动合成一条
  `{ ok: false, code: 'tool-not-executed' }` 的工具结果，明确告诉模型「该工具没有执行」。
- **部分正文补标记**：中断前已流出的正文会被补成 assistant 消息并追加
  「上一轮回复在生成中途被停止，以上内容不完整」，让下一轮知道该接着写而不是从头重来。
  `runCustomTurn()` 的 catch 里新增 `recordInterruptedTurn()`，把已流出的 `agent.text`
  同步进 `providerMessages` 落盘（旧数据没有这段也会由回放层从 items 补齐）。

有意保留的边界：`continueFrom`（把对话转成工作区助手）仍然只继承 `completed` 轮次，
`test-codex-mode.mjs` 明确钉着这条契约 —— 转助手意味着换执行环境，不该带着半截任务进去。

## 2. 硅基流动（vLLM / SGLang 后端）的工具调用被误判

`provider-protocols.mjs` 原来对 OpenAI 兼容协议过于严苛，命中的全是这类服务端的常见形态：

| 现象 | 原行为 | 现行为 |
| --- | --- | --- |
| 后续分片带 `id: null` / `name: null` / `arguments: null` | 跳过 `undefined` 不跳 `null` → 「格式不正确」 | 两者都跳过 |
| 每个分片重复发送 `function.name` | 只对 `id` 去重 → 工具名拼成 `read_fileread_file` | 以已声明工具名做权威前缀合并 |
| 单工具调用省略 `call.index` | 「模型输出索引格式不正确」 | 只有一个调用时默认 `0`；多调用缺索引仍拒绝（不猜顺序） |
| `call_id` 含 `:` 或 `.`（如 `call_0:1`） | 正则只允许 `[\w-]` | 放宽到 `[\w.:-]` |
| 无参工具返回 `arguments: ""` | JSON 解析失败 | 兜底成 `{}` |
| 完整 `tool_calls` 但 `finish_reason: "stop"` | 「工具调用与模型结束原因不一致」 | 归一化为 `tool_calls` |
| `usage` 里有 `null` 子字段 | 「token 用量格式不正确」 | 忽略该字段 |
| 一次回复给出 2 个工具调用 | 「此请求不允许并行工具调用」整轮废掉 | 顺序执行（循环本来就是逐个执行） |

最后一条值得单独说：`parallel_tool_calls: false` 是**请求侧**的开关，很多服务端会忽略它。
既然 `runCustomTurn` 本来就是顺序执行多个工具调用，为一个被忽略的字段废掉整轮没有收益。
该参数现在只决定要不要往 payload 里发这个字段。

## 3. 手机端附件：从「只能引用工作区文本」到「选了就能发」

后端新增 `POST /attachments`（复用既有的 nonce / origin / session / workspace 校验），
请求体上限单列 48 MiB（32 MiB 文件 Base64 后约 43 MiB）。文件落盘到工作区的
`.codex-uploads/<base36 时间戳>-<原名>`：

- 文件名只用于显示，不做路径拼接；拒绝路径分隔符、控制字符、`.`/`..`、超长名；
- `flag: 'wx'` 写入，同名不覆盖；
- 落盘后按 magic bytes 判定类型，不信任扩展名。

注入分三种块，都进同一条上下文：

- 文本：`<workspace-file path="...">`，超过 128 KiB 只取前 128 KiB 并标 `truncated="128KiB"`，
  同时提示「完整内容请用工具按路径读取」——**不再因为文件大直接拒绝整条消息**；
- 图片（PNG/JPEG/GIF/WebP，≤4 MiB）：`<workspace-image>` 说明 + 真正的图像块；
- 其他二进制（PDF、压缩包）：`<workspace-attachment bytes=...>` 只给路径，模型自己调工具读。

单条消息的引用上限从 5 提到 10。

### 图片多模态

一个中立块 `{ type: 'image', mime, data }`，由协议层各自映射：

- Chat Completions → `{ type: 'image_url', image_url: { url: 'data:image/png;base64,...' } }`
- Anthropic Messages → `{ type: 'image', source: { type: 'base64', media_type, data } }`
- Responses → `{ type: 'input_image', image_url: 'data:...' }`

几个必须处理的细节：

- **只内联本轮**。`inlineUserImages()` 只替换最后一条 user 消息；`providerMessages`
  落盘仍是路径说明。否则 4 MiB 的图 Base64 后 5.3 MB，几轮就会把 `sidebar-threads.json`
  和 4 MiB 的历史预算撑爆。下一轮模型仍能按路径用工具重读。
- **预算分开算**。`validateMessages()` 把图片字节从 1 MiB 文本预算里剥离，图片另有 8 MiB
  总上限；纯文本历史仍然是字符串，一个像素都不会碰没发图的老对话。
- **类型按字节判定**。改了后缀的 txt 不会被当成 `image/png` 发给上游，避免整轮 400。
- **原生 CLI 引擎不吃内联图**。那条路径仍然把图片当工作区文件、只给路径（README 已写明）。

前端 `+` 菜单新增「添加手机文件」「添加图片」，复用 `MainActivity` 已接好的
`onShowFileChooser`（安卓侧连 Photo Picker 的 ClipData-only 结果都处理过，Kotlin 无需改动）；
上传走 Base64 JSON，成功后把路径塞进 `state.files`，与「引用工作区文件」共用同一条注入链路；
上传中显示 chip 并阻断发送。

运行态体验同步向 DSH 看齐：

- 任务运行中 `+` 菜单不再整体锁死 —— 附件与引用可以继续准备，新建对话 / 切模式 / 换模型仍锁定；
- 命令与文件变更卡片在运行中直接在摘要里露出**末尾一行输出**（`tailLine`），不用点开折叠项
  才知道在跑什么。
