# v0.9.81：五项环境修复出包（glibc DNS、JS 源、JVM 壳、profile 软链）

日期：2026-11-24　产物：`dist/Kxxy-0.9.81.apk`　versionName `0.9.81` / versionCode `981000`

这一轮把此前只在源码里落地的五项修复**打进了可安装的 APK**。出包过程中还发现两处
只有走到打包环节才会暴露的问题（运行时里的路由脚本副本、扩展池未重建），一并处理，
并为此新增了一个最小重封工具。

---

## 1. 进包的五项修复

| # | 问题 | 落点 | 设备侧生效方式 |
|---|---|---|---|
| 1 | glibc 容器内 DNS / localhost 不可用 | `kxxy-glibc.sh`（pick 链 + bind）、`kxxy-glibc-provision.sh`（先探 `getent hosts ports.ubuntu.com`）、`RuntimeInstaller.ensureHosts()` | 扩展池体积变化 → extinstall 重新装配 |
| 3 | npm 每次运行报未知配置 | `ensurePnpmImportMethod` 改写 `~/.config/pnpm/rc`，迁移掉 `~/.npmrc` 里的旧块；env 改 `pnpm_config_package_import_method` | 引擎启动时幂等重写 |
| 2 | npm / pnpm / yarn 源不统一 | `buildEnv` 补 `pnpm_config_registry` / `YARN_REGISTRY` / `YARN_NPM_REGISTRY_SERVER`；新增 `ensureJsRegistry` 写 `.npmrc` / `.yarnrc` / `.yarnrc.yml` 管理块 | 同上 |
| 4 | `JAVA_TOOL_OPTIONS` 的 `Picked up …` 污染输出 | 删掉该变量；`ensureJvmWrappers` 把 `lib/jvm/<jdk>/bin/{java,javac,jar,javadoc,jshell,keytool}` 换成壳 + `<name>.real` | 每次启动幂等重写 |
| 5 | profile 缺 `node_modules` | `ensureProfileLinks` 按 manifest 给预装包建软链；`ensurePreinstalledDependency` 把声明写成 `file:<engine>/lib/node_modules/<pkg>` | 每次启动幂等修链 |

第 4 项只覆盖 `lib/jvm/<jdk>/bin`，`$JAVA_HOME/bin/java` 与 PATH 上的 `java` 软链
天然一起覆盖；参数由 `EngineConfig.jvmDefaultFlags()` 提供（tmpdir / user.home /
时区 / jansi），换时区后重启即按新值重写壳。

## 2. 出包时才暴露的两件事

### 2.1 `verify-runtime` 报「路由未与当前源码同步」

`kxxy-glibc.sh` 在运行时里**还有第二份**：`libexec/python-default/kxxy-glibc`。
它是裸 `python3` / `pip` 路由的容器入口（`python-default.py` 直接 exec 它），
由 `tools/lib/python-default.mjs` 从同一份源码生成，`verify-runtime` 会逐字节比对：

```
默认 Python/原生工具：✗ 路由未与当前源码同步：libexec/python-default/kxxy-glibc
结论：1 个关键条目缺失
Runtime verification failed; refusing to package
```

整包重跑 `build-runtime.mjs` 代价过大（2.5 GiB / 7.7 万条目，且会顺带改动
Python 修复资产的字节绑定），所以新增

**`tools/sync-glibc-route-runtime.mjs`**：只替换这一个条目、其余条目原始压缩字节
整段搬运，重封后更新 `build.json` 的 sha256 / 体积 / 未压缩字节；脚本自带结构复核
（条目数不变、除该条外名称/大小/CRC 全等）与「`--out` 不可覆盖」保护。

```bash
node tools/sync-glibc-route-runtime.mjs \
  --in .cache/apk-assets-hold/runtime.zip \
  --out .cache/runtime-0.9.81/runtime.zip \
  --meta android/app/src/main/assets/meta/build.json
```

结果：`5,299 B → 6,931 B`（+1,632），条目数仍 `76,982`。

### 2.2 老设备不会自动拿到新的路由脚本 ⇒ 新增就地自愈

运行时里的那份脚本只是**内容变了**：不新增文件、不动 `RUNTIME_VERSION`，
`isComplete()` 的十几个锚点全部通过，于是装上新 APK 也不会重新解压运行时
（真机 2.5 GiB 解压 6–10 分钟，用户机器常年只剩几个 GB，不值得为一个 6.9 KiB
的脚本这么做）。

新增 `RuntimeInstaller.healPythonRouteScript()`：盘上那份不含新标记
（`GUEST_ETC=`）且扩展里那份已带标记时，直接把扩展的 `bin/kxxy-glibc` 覆盖过来
（同一份源码、同一套占位符回填，路径完全等价），先写 `.heal` 再 rename，中断不会
留下半个脚本。调用点三处：启动快路径、全量安装、`maintainAfterHealthy` 步骤表。
扩展还没重装好时它什么都不做，下一轮启动自然收敛。

## 5. 设备侧会发生什么

1. **升级安装**后首次启动：`ensureHosts` 写 `engine/etc/hosts`，`ensureJvmWrappers`
   把 JDK 启动器套壳（三种状态幂等），`ensureProfileLinks` 修软链，
   `ensureJsRegistry` / `ensurePnpmImportMethod` 重写配置块。
2. **glibc 扩展**：池字节数从 `29,874,109` 变 `29,875,408`，extinstall 的
   `poolSignature` 判为落后 → 重新装配扩展目录（`bin/` 与 `rootfs` 种子）。
   用户 apt 装的东西在 `$FILES/glibc/rootfs`，不在扩展目录里，**不会丢**。
3. **默认 Python 路由**：下次启动 `healPythonRouteScript` 用扩展那份覆盖
   `libexec/python-default/kxxy-glibc`。若扩展还没重装好，这一次跳过，再下次收敛。
4. **不需要重装运行时**：没有任何新锚点，`isComplete()` 仍判真，启动不重解压 2.5 GiB。

## 6. 未验证 / 风险（不要当成已通过）

- **未安装到任何设备**。本轮只有构建机侧校验：Kotlin 编译通过（1 条既有
  `forEach` label 警告，非本轮引入）、脚本 `sh -n`、池与运行时内容逐项核对。
- **JVM 壳**在真机上的实际行为未验：`gradle --version`、`kotlinc`、`mvn -v`
  尚未跑过。回滚方式：把 `bin/java.real` 改名回 `bin/java` 即可（或直接重装运行时）。
- **`file:` 依赖声明**（第 5 项）仍有上次留下的风险：上游 `dsh-app-boot`
  若把 `dependencies` 当 semver 解析可能拒绝。装后第一件事看 `dsh web` 能否起来、
  插件页是否仍显示「已安装」；有问题只需还原 `ensurePreinstalledDependency`。
- numpy 2.5.4 / psutil 7.2.2 的旧 Android wheel 标签仍在，需应用内自检判定。
- 第 3 项的验收要在设备上跑：`npm -v 2>&1` 无警告、
  `pnpm config get package-import-method` = `copy`、
  `npm/pnpm/yarn config get registry` 三者同源。
