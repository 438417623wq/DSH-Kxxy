# 插件崩溃兜底（kxxy-guard）

> 起因：用户反馈「安装插件很容易崩溃。不兼容按道理来说，我移植的是桌面端，应该是完美兼容的呀，就哪怕不兼容也不应该崩溃」。后一句是对的 —— 这就是本次修改的唯一目标：**插件可以坏，宿主不能被它带走。**

## 一、崩溃是怎么发生的

引擎是一个 Node 进程跑到底的：

```
engine/bin/node --expose-internals <runtime>/lib/node_modules/@deepseek-ai/dsh/lib/bin.js web --patch …
```

第三方插件与官方内核**共享同一个进程、同一个事件循环**。而 Node 的默认语义是：

| 情形 | Node 默认行为 |
|---|---|
| 一个没人 `catch` 的 Promise 被 reject | **进程退出**（node ≥ 15，`--unhandled-rejections=throw`） |
| 异步回调里抛出的异常（`setTimeout` / socket 事件 / native addon 回调） | **进程退出** |
| 插件 `import` 失败 | cordis Loader 已兜住（`log.error` 后 return） |
| 插件 `apply()` 里同步抛错 | cordis fiber 接住，标记该插件失败 |

也就是说：**装载环节是隔离的，运行环节不是。** 移植到手机上的桌面插件，最常见的死法恰好落在后者 —— 它在一个定时器 / 事件监听 / 后台轮询里调了个桌面或 Electron 才有的 API，抛出 `TypeError`，没人接，于是整个引擎连同一个正在跑的会话一起消失。

用户看到的是「装了插件，用着用着整个应用崩了」，而真实粒度只是「那一个插件报错了」。

## 二、修法：给引擎进程加一层 preload 兜底

新增 `android/app/src/main/assets/guard/kxxy-guard.cjs`，由 `EngineConfig.buildEnv()` 注入：

```
NODE_OPTIONS=--require "<files>/kxxy-guard.cjs"
KXXY_GUARD_DIR=<files>/kxxy-home/guard
KXXY_GUARD_MAIN=1
```

它做三件事：

1. `process.on('unhandledRejection')` / `process.on('uncaughtException')` 接住异常，**引擎继续跑**；
2. 把事件写进 `<home>/guard/guard.log` 与 `guard-state.json`（结构化的最近 5 条），供体检页读取；
3. 从调用栈里认 `node_modules/<pkg>` 做归因，并用「是否在 `app.asar` 里」区分内核与插件。

选 `--require` 而不是改引擎入口，是因为入口在**只读的 asar** 里；而 preload 对 ESM 入口同样生效（Node 22 与真机 Node 24 都验过）。

## 三、四条硬约束（每条都踩过）

1. **文件不存在就不注入。** `--require` 找不到文件是**启动期致命错误**，比没有兜底严重得多 —— 引擎会连起都起不来。`buildEnv` 里先 `isFile && length > 0` 才拼 `NODE_OPTIONS`。
2. **路径必须加双引号 + 换正斜杠。** `NODE_OPTIONS` 按空格切分（本仓库路径 `dsh kxxy` 就带空格，实测报 `Cannot find module 'E:\deepseek-harness\dsh'`）；而引号内的 `\` 是转义符，`\d` 会变成 `d`，Windows 路径会连成一串字母。Android 上路径本来就没有空格且用 `/`，这两条是为了让同一份逻辑在构建机上也成立。
3. **只装在主引擎进程里。** `NODE_OPTIONS` 会被子进程继承 —— 插件去跑 `npm install` / `tsc` 时，那些子进程本该「该崩就崩」，被兜住会表现为**构建卡死**。所以用 `KXXY_GUARD_MAIN=1` 做一次性开关，guard 读完立刻 `delete`，之后 fork 的子进程只继承 `NODE_OPTIONS`、看不到开关，安静退出。同理**不注入** `--unhandled-rejections=warn`（它同样会被继承，等于全局改了子进程语义）。
4. **兜底不是无限兜。** 同一句错误连续 3 次、或 60 秒内超过 60 次，说明进程已不可信（端口占着、事件循环里死循环报错），此时主动 `exit(1)` 交给原生监管循环重启 —— 留一个半死的进程比重启更糟。

另外，guard 整体包在一个 `try/catch` 里：**它自己坏了就安静退回 Node 默认行为**，绝不因为兜底模块的 bug 让引擎起不来。

## 四、可见性：体检页新增「异常兜底」

只兜不报等于把问题藏起来，所以 `health.mjs` 新增第 7 项 `GUARD`，并引入第四种判定 `WARN`：

| verdict | 含义 | 界面 |
|---|---|---|
| `OK` | 兜底已生效，本轮 0 次拦截 | 绿 ✓ |
| `WARN` | 已兜底 N 次，引擎活着 | 橙 `!` + 徽章「已兜底」 |
| `UNKNOWN` | 本轮没注入兜底 / 状态文件读不出来 | 灰 – |
| `BAD` | 启动配置坏了 | 红 ✕ + 修复入口 |

`WARN` 刻意**不**参与「修复」判定：修复动的是 profile 补丁（会连带搬走主题、模型配置），而插件的运行时错误跟启动配置无关——点错了反而制造新故障（参见 README 缺陷 BW / CA）。提示语直接把用户推向正确动作：

> 疑似来自插件 `dsh-plugin-notify`：到对话页侧栏 →「插件」停用它即可。这类错误不影响启动，不需要「修复」

## 五、验收

`tools/test-guard.mjs`（21 项断言，本地可跑）：

- `[1]` 未捕获 rejection：进程存活、state 记录 1 次、kind 正确；
- `[2]` 定时器回调抛错：进程存活、记为 `uncaughtException`、日志落盘；
- `[3]` 子进程**不**继承兜底：子进程仍按默认行为失败退出，错误照常冒泡；
- `[4]` 同一条错误连续 3 次：主动 `exit(1)`，日志写明 `give-up`；
- `[5]` 缺 `KXXY_GUARD_MAIN`：完全不接管，进程按默认行为死亡；
- `[6]` 栈归因：profile 下的插件帧报 `fake-plugin` / `core=false`，
  引擎根下的内核帧报 `@deepseek-ai/dsh-core` / `core=true`
  —— 这一条是「别把内核的锅甩给插件」的回归防线。

```
node tools/test-guard.mjs   →   21 通过 / 0 失败
```

体检项用伪造的 `guard-state.json` 验证过输出：

```
WARN  已兜底 3 次异常，引擎没有退出。最近一次：uncaughtException · dsh-plugin-notify —— TypeError: …
```

## 六、这层兜底**不**覆盖什么

- **native 崩溃**（插件里 `.node` 的 `SIGSEGV`）、`process.exit()`、**OOM**：信号级死亡，JS 层接不住。这类由原生 `EngineSupervisor` 的重启 + 退避 + 确定性失败判定（README 缺陷 BT/BU）处理；
- **安装过程本身失败**（下载/解包/构建脚本报错）：不走引擎主进程，属于插件管理器的错误路径；
- **插件把引擎配置写坏**（cordis.patch.yml 语法错）：那是启动期失败，归 `checkPatchFile` 与原生修复链（方案 K）。

换句话说：这层解决的是「插件运行期把宿主拖死」，不是「插件安装失败」。两者在真机上的表象都是「崩了」，但归因路径完全不同，混在一起修只会两边都不准。
