# 图片模态兜底与 glibc 离线预置（v0.9.93）

上一版（v0.9.89）为「自定义路由发图被拒」加的是**目录回退**：按协议映射 + 模型名
规范化去内置目录里找同族条目，找到就把 `input` 继承过来。这一版的起点是一句反驳：

> 三条路由 key `guiji` / `chat` / `guge` 仍都不在 pi-ai 内置目录里，所以永远查不到
> base，图片模态无从继承。

这句话是对的。目录回退只在「模型名能在内置目录里对上某个已知多模态条目」时生效
（`gpt-6.2-astra` → `gpt-6-astra` 这类同族演进），而中转路由的模型名往往是上游自造
的，整条链最后还是落回 schema 默认的 `["text"]`。所以这一版把最后一格从「查目录」
改成「看协议」。

## 一句话结论

| # | 现象 | 真根因 | 本轮改法 |
| --- | --- | --- | --- |
| 1 | 自定义路由发图仍报「当前模型不支持图片」 | 目录回退只能覆盖「内置目录里有同族」的模型名；完全未知的名字仍然取 `["text"]` | `unknownRouteInput()`：**对话协议**在目录与回退都落空时按可收图放行（已知纯文本仍拦截；`KXXY_MODALITY_UNKNOWN=strict` 可关闭）；补丁集 `@41 → @42` |
| 2 | LibreOffice 只有 WASM 后端 | 上游无 android 原生包，且 kit 的 native 路径要 `dlopen` glibc 版 `libreofficekit_hook` | **不做**，把边界写死（见 §2）：WASM 是架构，不是故障 |
| 3 | `dotnet` / `julia` / `wkhtmltopdf` 首次使用要联网 | 预置脚本原样调用 `apt` / `curl`；`.provisioned` 为空时等于「装了扩展也用不了」 | 三份**离线包**随 glibc 扩展进池，`kxxy-glibc-provision` 本地包优先、断网可装；拿不到才回退联网 |

## 1. 图片模态：最后一格不能查目录

判定链没变（还是上游那三处），变的是最后一个 fallback：

```js
input: declaredInput(entry.input)
    ?? (request.defaultInputDeclared === true ? declaredInput(request.defaultInput) : void 0)
    ?? base?.input
    ?? modalityBase?.input                       // 目录回退（v0.9.89）
    ?? unknownRouteInput(api, request.defaultInput)   // 协议兜底（本轮）
```

`unknownRouteInput` 只回答一个问题：**这个 route 说的是不是对话协议**。

- `openai-completions` / `openai-responses` / `anthropic-messages` /
  `google-generative-ai` → 在 `defaultInput` 基础上补 `image`；
- `openai-embeddings`、`api` 缺失、其它非对话协议 → 原样返回，embedding 不会被
  放宽成可收图；
- 已经声明过 `image` 的不重复追加；
- `KXXY_MODALITY_UNKNOWN=strict` 退回「未知即纯文本」的旧判定。

为什么可以按协议放行：这三种协议里，图片是消息内容的一部分，模型不支持时**上游会
自己返回 400**（`invalid content type` / `image is not supported`），这个报错比本地
一句「当前模型不支持图片」更准确 —— 后者把「我们不知道」说成了「模型不行」，而
真正的原因是本地目录不认识这条 route。

两条边界必须留住，否则「纯文本模型仍然拒绝图片」这条契约就破了：

- **目录明确说是纯文本的**（`deepseek-v4-pro`、`o3-mini`、embedding 类）→
  `knownTextOnlyModel()` 识别后原样返回，兜底不放行；
- **非对话协议 / `api` 缺失** → 不放行。

代价写在明处：目录**完全不认识**、又挂在对话协议上的模型，本地不再拦，由上游拒绝。
`request.defaultInput` 显式写成 `[text]`（profile 里加 `defaultInput: [text]`）仍然
是最高优先级，可以逐路由关掉兜底。

### 为什么「代码没变」也可能是真的

真机上如果 `lib/node_modules/@deepseek-ai/dsh-llm-pi-ai/lib/index.js` 里搜不到
`KXXY_CATALOG_MODALITY_FALLBACK`，那不是补丁没写，而是**设备上的运行时没换**：
设备只在 `patchset.version` 与 APK 里的 `PATCHSET_MARKER` 不同时才重解压。本版把
标记推到 `@42`，装上新 APK 后必然重新解压一次 —— 顺手把「旧运行时 + 新配置」这种
半新半旧的状态清掉。

复核命令（设备上，`run-as app.kxxy`）：

```sh
grep -c KXXY_CATALOG_MODALITY_FALLBACK files/engine/lib/node_modules/@deepseek-ai/dsh-llm-pi-ai/lib/index.js
grep -c unknownRouteInput files/engine/lib/node_modules/@deepseek-ai/dsh-llm-pi-ai/lib/index.js
cat files/engine/lib/node_modules/kxxy-host/patchset.version    # 应为 kxxy-patchset@42
```

## 2. LibreOffice：把「不做」写清楚

`soffice` / `libreoffice` 在 Android 上没有官方产物；`@deepseek-ai/libreoffice-kit`
的 native 路径要靠 `dlopen` 加载 glibc 版的 `libreofficekit_hook`。我们的宿主进程是
bionic（Node），跨 ABI `dlopen` 不可能成功；要在 proot 里跑，就得让 kit 改成
「起一个 glibc 子进程 + `soffice --headless`」这套 CLI 协议 —— 那是重写后端，不是加
一行 fallback，还要一份 400–500 MB 的 `office-native` 套件与真机转档验收（中英文、
表格、公式各一轮，看字形嵌入与内存峰值）。

所以本版维持 `libreoffice-kit-wasm`，并且明确：

- **WASM 不是回退，是当前架构**。`patchLibreOfficeKitPlatform` 在 Android 上只放行
  WASM，是为了不冒充 Linux glibc ABI —— 冒充过一次（manylinux 垫层）的代价已经付过。
- 能力探测里看不到 `soffice` 是**预期**，不是缺失项；office 转 PDF 走 WASM 即可用。

## 3. 离线预置：三份包随扩展进池

`kxxy-glibc-provision` 原来只有联网路径。断网时 `julia` / `dotnet` / `wkhtmltopdf`
首次调用必然失败，`.provisioned` 目录空着 —— 这不是「没预置」，是「没法预置」。

现在三份产物在**构建期**下好、钉死摘要，作为 glibc 扩展的资产一起进池
（`<root>/extensions/glibc/provision/`）：

| 包 | 来源 | 体积 | 设备侧落点 |
| --- | --- | --- | --- |
| `julia-1.11.7-linux-aarch64.tar.gz` | 官方 aarch64 tarball | 285 MiB | `/opt/julia-1.11.7` |
| `dotnet-sdk-8.0.404-linux-arm64.tar.gz` | 微软官方 SDK | 199 MiB | `/opt/dotnet` + `/usr/bin/dotnet` 包装器 |
| `wkhtmltopdf-noble-arm64-debs.tar.gz` | noble/arm64 完整依赖闭包 | 91 MiB | `dpkg -i` 一次装齐 |

生成入口：`node tools/fetch-provision-bundles.mjs`（`--only julia|dotnet|wkhtmltopdf`）。
闭包里 119 个包，`libc6` / `libstdc++6` / `libgcc-s1` / `zlib1g` 这些**base rootfs
已有的**会被跳过 —— 判据是解出 base 归档里的 `var/lib/dpkg/status`，按 dpkg 版本语义
比较约束，不是按名字猜。

设备侧 `kxxy-glibc-provision` 的新顺序：

1. `<ext>/provision/<包>` 在 → 直接装（tar 解包 / `dpkg -i`），**不联网**；
2. 不在 → 走原来的 `apt` / `curl`（断网会失败，但报错里给出的重试命令仍然有效）；
3. 装成功才写 `.provisioned/<目标>`，重复执行直接跳过；
4. 装成功后**删掉用过的离线包**（`KXXY_PROVISION_KEEP=1` 可保留）：三份包在扩展目录里
   占 ~580 MiB，而装好的东西落在 `<files>/glibc/rootfs`，重装扩展或升级 APK 都不会丢 ——
   留着只是让每台设备多背一份压缩包。删掉也能恢复：重装扩展会重新释放。

`dotnet` 的包装器固定 `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1`：base rootfs 没有
libicu，不设这一条 `dotnet --version` 会以 `Couldn't find a valid ICU package` 退出。
`DOTNET_ROOT=/opt/dotnet` 也在这里给，所以 `dotnet` 仍然是**一条普通命令**。

`dpkg -i` 的退出码**不作为判据**：proot 里 postinst 会碰到取不到的 `/dev`、`/proc`
或 locale 设置而返回非 0，但文件已经落盘。这里把 dpkg 的失败降级成「打印日志尾巴」，
真正的判据是紧接着的 `wkhtmltopdf --version` —— 能出版本号才算装好，装不出来的
才会真的失败。闭包本身另行离线核对过：119 个包的 `Depends` / `Pre-Depends` 全部能在
「闭包 ∪ base rootfs 的 91 个已装包」里满足（`libc6` / `libstdc++6` / `libgcc-s1` /
`zlib1g` 这些 base 已带的不会重装）。

`kxxy-py` 没有随包离线化：它是容器里的 python 3.12 + manylinux 轮子，裸 `python3`
已经能回落到原生 bionic 3.14（v0.9.89 起），断网时用裸 `python3` 即可。

## 契约与版本

- `PATCHSET_MARKER` `@41 → @42`（`build-runtime.mjs` / `RuntimeInstaller.kt` /
  `test-runtime-capability-contracts.mjs` 三处同步）—— `dsh-llm-pi-ai` 补丁内容变了；
- glibc 扩展 `24.04.3-r3 → r4`（新增三份 provision 资产，设备会重新拉取该扩展）；
- 回归：`tools/test-model-modality-fallback.mjs` 新增 10 条（四协议放行、带网关前缀、
  非对话协议不放行、协议缺失不放行、已声明不重复、**已知纯文本不被兜底放行**、
  `strict` 关闭兜底、产物里不得再出现 `?? [...request.defaultInput],`）。

## 仍需真机确认

1. `chat` / `guge` / `guiji` 发图不再报「当前模型不支持图片」；同一路由上的纯文本
   模型改为**上游**拒绝（而不是本地拦截）；
2. 飞行模式下 `julia --version` / `dotnet --version` / `wkhtmltopdf --version`
   首次即可用（三份离线包在扩展里）；
3. `dpkg -i` 装 119 个 deb 后 `wkhtmltopdf` 能真的把 HTML 转出 PDF（字形与中文字体）；
4. `dotnet` 无 libicu 时的 invariant 模式是否影响 SDK 常规命令（`new` / `build`）。
