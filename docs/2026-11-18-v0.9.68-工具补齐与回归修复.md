## 1. 硬链接：为什么修不了，以及修不了之后怎么办

### 1.1 取证

四条独立证据指向同一个结论：**不是 f2fs 的问题，是这台 ROM 的 SELinux 策略**。

| 试验 | 结果 |
| --- | --- |
| app 私有目录 `ln a b`（Termux coreutils） | `Permission denied` |
| app 私有目录 `/system/bin/ln`（toybox） | `Permission denied` |
| `/data/local/tmp` 以 `shell` 身份 `ln` | `Permission denied` |
| Python 直接 `libc.link()`（`ctypes`） | `-1`，**errno 13 = EACCES** |
| `mount \| grep " /data "` | `f2fs (rw,lazytime,seclabel,nosuid,nodev,noatime,...)` —— 无任何限制性选项 |

`EACCES` 而不是 `EPERM`/`EOPNOTSUPP`，说明内核不是「文件系统不支持」，而是
**LSM 在 `inode_link` 处拒绝**；连 `shell` 域在 `/data/local/tmp` 都被拒，说明策略
是设备级、而不是「app 沙箱内才禁」。改它需要 root（`setenforce 0` / magisk 模块 /
自己编 sepolicy），任何 APK 都做不到 —— 这不是「没做完」，是权限模型的边界。

> 顺带解释 `rsync --link-dest`：它内部就是 `link(2)`，被拒后按设计回落到复制，
> 所以 `base/dst` inode 不同（`3234530` vs `3234547`）**正是预期行为**。
> 复制是语义正确的降级，代价只是多占一份空间。

### 1.2 我们能做的两件事

**① `bin/ln` 退化包装器**（`build-runtime.mjs` 的 `hardlinkWrappers()`）

先按原样调多调用入口 `bin/coreutils ln`（`bin/ln` 本来就是指向它的软链）：

- `ln -s` 一律原样透传 —— 软链是另一条权限（`untrusted_app` 有），从不受影响；
- 失败且 stderr 是 `Permission denied` → 用 `cp -a` 落一份独立副本，并在 stderr 写明
  「已退化为独立副本」；
- 源不存在、目标非目录却给了多个源、以及其他错误 → **不退化**，原样报错
  （否则「找不到文件」会被伪装成一次成功的复制）；
- `KXXY_LN_STRICT=1` 关掉退化，恢复 POSIX 语义（脚本确实依赖「改一处即改两处」时用）。

**② pnpm 的导入方式钉成 copy**

pnpm 默认 `package-import-method=auto`：先 `clone`，再 `hardlink`，最后才 `copy`。
在必挂的 `hardlink` 上反复试探没有意义，`EngineConfig` 里直接给
`npm_config_package_import_method=copy`。

## 2. Python 科学计算 + pandas 回归：一份陈旧的 stage

### 2.1 现象与根因

现象很怪：`numpy 2.5.4` 正常，`pandas` 却 `ModuleNotFoundError`；而种子表里
（`tools/lib/seeds.mjs`）明明写着 `python-lxml`、`python-pillow`、`python-pandas`、
`matplotlib`。

设备上 `site-packages/` 只有七个条目：

```
cffi  cryptography  numpy  pip  proot_distro  psutil  pycparser
```

真因不在 Python，而在**装配链**：

```
fetch-runtime.mjs   →  .cache/debs/*.deb + manifest.json      （11-18 更新过，290 包）
debextract.py       →  .cache/stage/{entries.json,blobs}      （停在 10-25，279 包）  ← 问题
build-runtime.mjs   →  runtime.zip                            （读 stage，合法但残缺）
build-apk.ps1       →  APK                                    （只看 runtime.zip 在不在）
```

`build-apk.ps1` **从不碰 stage**。改了种子表、拉了新 deb、却忘了手动重跑
`debextract`，打包链就会安静地用几周前的闭包出包：产物完全合法（条目齐、摘要对、
能解压），只是少了新加的包。这类错误不抛异常、不打日志，只能靠比对清单发现。

> 用户看到的「17:40 还正常」是上一份 runtime 的缓存/旧安装；0.9.67 重装后
> 落到同一份陈旧 stage 上，于是 pandas 消失。**这不是 pandas 坏了，是它从来没进包。**

### 2.2 三处修复

1. **重解 stage**：`node tools/prepare-stage.mjs` → 295 包 / 47466 条目。
2. **守卫**：新增 `tools/lib/stage-fresh.mjs`（唯一判据）+ `tools/prepare-stage.mjs`
   （按需重解）；`build-runtime.mjs` 在用默认 stage 装配前**断言**一致，
   不一致直接报错并给出要跑的命令。判据三项：`entries.json` 不存在 /
   包集合（`name@version`）与清单不一致 / `entries.json` 比清单旧。
   解包原地进行（blobs 内容寻址），不「先删再建」—— 8 GiB 量级的递归删除既慢
   又容易触发批量删除审计。
3. **让老设备真的重解**：`PATCHSET_MARKER` 26 → 27。`isComplete()` 的十六条锚点
   全是「既有文件还在不在」，**新增文件一条都看不见**。不涨这个编号，0.9.67 升
   上来的设备会认为运行时完好、跳过解压，site-packages 里照旧没有 pandas。
   （`build-runtime.mjs` 与 `RuntimeInstaller.kt` 两处同步。）

### 2.3 新增的预装包

| 包 | 版本 | 边际体积 | 说明 |
| --- | --- | --- | --- |
| `python-scipy` | 1.18.1 | 12.0 MiB / 2 包 | 科学计算本体；sklearn 那类纯 Python 上层库随后 `pip install` 即可（只依赖 numpy/scipy 的 ABI） |
| `typst` | 0.15.1 | 13.7 MiB / 1 包 | 现代排版引擎，单二进制无依赖 |

| `pnpm` | 12.22.0 | 16.1 MiB | 见 §4 |

## 3. `irb`：一行 `GEM_PATH` 的事

`Gem::GemNotFoundException: can't find gem irb (>= 0.a)` 看起来像「没打包」，实际
`bin/irb` 与 `gems/irb-1.16.0/` 都在 **ruby deb 里**（`reline`、`debug` 同样是默认 gem）。

真正的原因：`EngineConfig` 里

```kotlin
"GEM_HOME=$HOME/.gem"
"GEM_PATH=$HOME/.gem"        // ← 只有这一条
```

RubyGems 的 `Gem.path` **完全由 `GEM_PATH` 决定**（有它就不再追加默认目录），
于是 `Gem.bin_path('irb', …)` 扫不到 `<root>/lib/ruby/gems/4.0.0/` 下的规格。
`ruby -e` 本身照跑（核心库走相对路径），所以症状只在 `irb`/`gem list` 上暴露。

修复两处（因为 ruby 是**扩展池**里的一项，装完再开终端要跟着变）：

1. 引擎进程环境：`GEM_PATH=$HOME/.gem:<root>/lib/ruby/gems/4.0.0`（用户目录在前）；
2. 终端启动脚本：按磁盘现状把 `<root>/lib/ruby/gems/*` 补进 `GEM_PATH`
   （与既有的 `RUBYLIB` 重算同一条理由 —— 环境变量是引擎启动时的快照）。

## 4. pnpm / corepack：把「首次运行联网」这件事拿掉

### 4.1 症状与根因

`dsh plugin … list` 卡住，`timeout 120` 直接 124；单独 `pnpm --version` 150 秒不返回。
根因不是网络慢，而是 `bin/pnpm` 当时指向 **corepack 的 shim**：corepack 首运行要把
`packageManager` 字段（`pnpm@12.21.0`）整包从 registry 下载、解到
`~/.cache/node/corepack`，而这台设备上这一步既不 EOF 也不超时 —— 就那样吊着。

### 4.2 为什么不用 npm 上的 pnpm

pnpm 官方 12.x 的发行物是**原生可执行文件**（`@pnpm/exe.linux-arm64` 等，
只有 glibc / musl 两种 linux 目标，**没有 bionic**）；npm 包里只剩一个
「找不到就去 registry 现下载」的 shim。装到手机上，第一次运行照样要联网。

Termux 的 `pnpm` 包是源码编的**单文件可执行**（`bin/pnpm`，54.7 MiB，node SEA，
`DT_NEEDED` 只有 `libdl.so`），在 bionic 上直接跑，**不需要 node 参与**。

### 4.3 落地

- `SEED_PACKAGES` 增加 `pnpm`（`Depends: git` 由基线满足），进 runtime.zip；
- `bin/pnpm` / `bin/pnpx` 由闭包自带，**不再生成同名包装器**（会顶掉真二进制）；
- `bin/corepack` 包装器加一条改道：`corepack pnpm …` / `corepack pnpm@12.21.0 …`
  一律 `shift` 后 exec `$d/pnpm`（版本号直接丢掉：本地这份是构建期钉住的版本，
  corepack 的版本协商在这里没有意义）。

## 5. 新工具：进了预装 / 进了池 / 拿不到

| 工具 | 处置 | 体积（deb / 解包） |
| --- | --- | --- |
| `webpack` + `webpack-cli` | node-tools 池（npm 源，纯 JS） | — |
| `zig` 0.17.1 | 新池 `zig` | 52.6 MiB / 511 MiB |
| `dotnet` (SDK 8) | 新池 `dotnet`（`dotnet-sdk-8.0` 闭包 10 包） | 61.8 MiB / ~600 MiB |
| `python-torch` 2.15.0 | 新池 `torch`（`import torch` 即可用） | 36.0 MiB |
| `lfortran` 0.5x | 新池 `fortran`（Termux 没有 gfortran） | 17.1 MiB |
| `ltrace` | 预装 | 0.1 MiB |
| `typst` | 预装 | 13.7 MiB |

**拿不到的，以及为什么**

- `gfortran`：Termux 从 GCC 包里移除了 Fortran 前端，索引里没有；`lfortran` 是
  唯一可用的 Fortran 编译器（支持 F2018 的大部分，但 OpenMP 与老式扩展不全）。
- `julia`：Termux 主仓没有（历史上的 `julia` 包已下架），自建需要 LLVM 全量源码编译，
  在手机侧的收益与体积都不成立。
- `perf`：需要内核 `perf_event_open` 与匹配的 `vmlinux`；系统内核没开
  `CONFIG_PERF_EVENTS` 给应用域，且 `/proc/kallsyms` 不可读。`strace` / `ltrace` /
  `valgrind`(callgrind) 是这台设备上可用的替代。
- `python-scikit-learn`：Termux 索引里没有；但它**是纯 Python**，`pip install
  scikit-learn` 在 numpy+scipy 就位后可以直接落地（不再需要现场编译）。
- `cv2` / `opencv`：Termux 索引里没有 `opencv`，PyPI 的 aarch64 轮子是 manylinux
  （glibc）链接，bionic 加载器直接拒绝。图像处理走已预装的 `Pillow` + `imagemagick`。
- `wkhtmltopdf`：Qt WebKit 时代的老项目，Termux 索引里**没有**（`wkhtmltopdf*`
  零命中），自建要编整个 Qt WebKit —— 不成立。替代链是**已落地的两件**：
  `typst`（预装，0.15.1）+ `pandoc`（池，3.12.1），即
  `pandoc -f html -o out.pdf --pdf-engine=typst`。`weasyprint` 不在预装里
  （它要 pango/cairo 一整套原生库，Termux 得另装），`chromium --headless`
  需要 x11-repo，两者都不作为本版方案。

## 6. 复现步骤（构建机）

```bash
node tools/fetch-runtime.mjs                 # 拉 deb + 写 .cache/debs/manifest.json
node tools/prepare-stage.mjs                 # 解包 stage（清单变了才会真跑）
KXXY_POOL_ONLY=zig,fortran,dotnet,torch,node-tools \
  KXXY_POOL_OUT=.cache/apk-assets-hold/ext-pool \
  node tools/fetch-extensions.mjs            # 增量重打池 + 刷新 extensions.json
node tools/build-runtime.mjs \
  --stage .cache/stage --asar .cache/.rc3-res/resources/app.asar \
  --plugins plugins --out .cache/apk-assets-hold/runtime.zip
tools/build-apk.ps1 -Offline -Gradle <gradle.bat>
```

> `prepare-stage.mjs` 是这一轮新加的「必跑项」。忘了它会得到一份少了新包的
> runtime.zip，而 `build-runtime` 现在会直接报错拦住（判据见 §2.2）。
