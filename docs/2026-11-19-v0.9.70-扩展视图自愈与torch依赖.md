## 1. 扩展视图为什么会整体消失

`bin/` 与 `lib/` 是 runtime 的地盘，每次安装都被整体替换；扩展装进去的命令
（`ffmpeg`、`php`、`ruby`、`irb`…）是通过 `extensions/<id>/.links.json` 在
`<root>/bin` 里建的软链。安装器换完 `bin/` 之后写一个 `extensions/.relink`
标记，插件启动时看到标记就把这些软链重建一遍 —— 这是设计。

真机上塌掉的是**时序**：

1. `RuntimeInstaller` 在安装流程末尾（`writeStamp()` 之后）写 `.relink`；
2. 插件（`kxxy-host`）由 webServer 拉起，启动时机与安装并行，**可能先跑**；
3. 先跑时 `bin/` 还是空的、`extensions/` 还在，`relinkAll()` 按标记重建了一批
   链接，然后把标记删了；
4. 安装继续，`bin/` 被整体替换 —— 刚建的链接全没了，标记也已消费；
5. 下次启动 `isComplete()` 判真（文件都在），不再安装，也就不再写标记。

结果就是「扩展目录好好的、`.links.json` 好好的、命令一条都用不了」。

修法不能只靠标记（标记本身就是时序产物），所以在 `relinkAll()` 里加了一层
**廉价抽样**：遍历已装扩展，每个只看 `.links.json` 里头三条 `bins` 的目标在
不在盘上，任意一条缺就判「视图丢了」，整轮重建。代价是每次启动几十次
`existsSync`。

同时修掉一处自作聪明：原来无条件 `unlinkSync(marker)`，走兜底路径（本来就没
标记）时会抛 `ENOENT`，被外层 `catch` 吞掉 —— 行为对，但把「重建失败」和
「没有标记」两类错误混成了一种。现在只在 `hasMarker && seen > 0` 时删。

## 2. torch：装得上、导不进

`torch.pool`（374.7 MiB，12,407 个文件）装配是成功的，`extensions/torch` 里
`_C.so` 与 6 个 `.so` 都在、`LD_LIBRARY_PATH` 也接进去了。失败点在
`torch/__init__.py` 第 24 行：

```
ModuleNotFoundError: No module named 'typing_extensions'
```

与 pandas 那次是同一个病根：Termux 的 deb 不写纯 Python 依赖。`python-torch`
的 `Depends` 只有 `python`、`python-numpy`、`openblas` 这类原生件，
`typing_extensions`、`filelock`、`networkx`、`fsspec` 全部留给 `pip`；
而 Termux 主仓索引里这四个也是零命中。

本版把四个 `*-none-any.whl` 内置进 `site-packages`（`tools/lib/pydeps.mjs`）：

| 包 | 版本 | 为谁服务 |
| --- | --- | --- |
| typing_extensions | 4.16.0 | `torch/__init__.py` 直接 import |
| filelock | 4.2.12 | 权重/序列化文件锁 |
| networkx | 3.7 | `torch.fx` 图 |
| fsspec | 2026.9.0 | 各类存储后端抽象 |

**刻意不补 jinja2 / markupsafe**：MarkupSafe 只发平台轮子
（`markupsafe-3.0.4-cp314-…whl`），没有 `none-any`，我们的解包器只吃纯
Python 轮子；而它俩只服务 `torch.compile` / inductor 那条路径，核心张量运算
不需要。所以 `torch.compile` 在本机仍不可用 —— 这是体积（为一个可选路径再
引一个平台 ABI 补丁）与可用性的取舍，不是遗漏。

## 3. sklearn / cv2：确实是拿不到，不是没装

三条路都试过：

1. **Termux 主仓**：`python-scikit-learn`、`python-opencv`、`python-joblib`、
   `python-threadpoolctl` **全部零命中**（3,047 个包的索引逐条查过）；
2. **TUR（termux-user-repository）**：这个源曾经有 `python-scikit-learn`，
   现在 `tur.kcubeterm.com` 上所有 apt 路径都 302 到 GitHub 主页 —— 已经
   不再提供 apt 索引；
3. **PyPI**：`scikit-learn` / `opencv-python` 只发 `manylinux`/`musllinux`
   轮子，bionic 上 `dlopen` 不了；源码编译要 `gfortran`（本机没有，`flang`
   不兼容 OpenBLAS 的 `gfortran` ABI 约定）+ 完整 meson 构建链。

结论：这两个包在本机没有可信来源，**不发包**。能给的替代：

- 数值/线性代数/统计：`scipy` 1.18.1 + `numpy` 2.5.4 已在 `site-packages`；
  `sklearn` 常用能力里 `LinearRegression`、`PCA`、`KMeans`、`cross_val_score`
  都可直接用 `scipy.linalg` / `numpy.linalg` 十几行写出来；
- 图像处理：`PIL` 13.0.0（含 ImageFilter/ImageOps）+ `numpy` 足够覆盖
  resize/色彩空间/阈值/卷积；视频帧抽取用 `ffmpeg` 扩展池；
- 真正的机器学习推理：`torch` 池（本版补齐依赖后可用）。

## 5. 打包链上的一个自伤：`--manifest` 覆盖构建清单

本版第一次出包后真机**根本起不来**，界面停在「启动失败 / 配置可组装，
建议原样重试」，而 `kxxy-patchset` 一直是旧值 —— 连运行时安装都没走到。
logcat 里的真话是：

```
E KxxySupervisor: PythonRuntimeRepair$Refused:
  Python 离线修复：pythonRepairManifestSha256 必须是字符串；不会自动清空或重装用户运行时
    at PythonRuntimeRepair.loadManifest → preflight → RuntimeInstaller.install
```

`build-runtime.mjs` 收尾时写两份东西：

| 文件 | 形状 | 用途 |
| --- | --- | --- |
| `assets/meta/build.json` | 扁平 `schema:1` + `pythonRepairManifestSha256` / `kxxyHostFingerprint` / `kxxyHostMarker` | 原生探针的期望值来源，**必须**进 APK |
| `--manifest <path>` | 运行时清单 `schemaVersion:2` + `entries` / `placeholderPaths` | 构建机与 issue 用 |

两者**指到同一个文件**时，后写的（运行时清单）覆盖前者。于是 APK 里的
`build.json` 变成运行时清单的形状，`pythonRepairManifestSha256` 直接消失，
`PythonRuntimeRepair.preflight()` 在第一道校验就拒启。

这一版之前没人踩，是因为 `--manifest` 一直指在 `.cache/` 下。本版第一次
构建时图省事指到了 `assets/meta/build.json`，于是踩了个正着。

处置：`parseArgs()` 里加硬拦 —— `--manifest` 指向
`assets/meta/build.json` 直接抛错，错误信息写清后果与替代路径。
