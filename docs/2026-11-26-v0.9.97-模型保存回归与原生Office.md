# v0.9.97：模型设置无法保存的回归修复 + 原生 Office 后端 + 装完即预置

> 对应真机（Redmi K60 Pro / `22127RK46C`，Android 13）的反馈：模型板块红字
> `llm-pi-ai: provider "guiji" defaultInput must name at least one modality`、
> 图片发不出去、LibreOffice 仍是 WASM、`.provisioned` 为空。

## 1. 模型设置「无法保存」——本产物自己引入的回归（最要紧）

### 症状
设置 → 模型 → 新建提供商：Provider ID / API 地址 / 密钥 / 模型目录都填对了，
点「创建提供商」必失败，红字拦在表单底部：

```
llm-pi-ai: provider "guiji" defaultInput must name at least one modality
```

整个模型板块不可用（改不动、存不下）。

### 根因
v0.9.93 为了区分「用户显式声明 `defaultInput`」与「schema 物化出来的 `["text"]`」，
把 Cordis schema 里的

```ts
defaultInput: z.array(z.union(MODALITIES)).default([...DEFAULT_INPUT])
```

的 `.default(...)` 去掉了。这一步本身必要（不去掉，`defaultInputDeclared` 恒为
`true`，整条目录回退 + 协议兜底链会被短路，图片问题永远修不好）。

但设置页的 provider 表单是**按 JSON Schema 物化草稿**的：数组字段没有 `default`
时，草稿里就是 `[]`，提交上来也是 `[]`。而

```ts
const defaultInput = [...source.defaultInput ?? DEFAULT_INPUT]
```

只对 `undefined` / `null` 兜底，空数组原样展开成 `[]`，紧接着的
`if (defaultInput.length === 0) throw` 就把保存打死了。

### 修法
`patchDefaultInputEmptyArray`（`tools/lib/patches.mjs`）：语义上「空数组」不是
「声明了零种模态」（那不可能成立），而是「没声明」——

```ts
const defaultInput = Array.isArray(source.defaultInput) && source.defaultInput.length > 0
  ? [...source.defaultInput]
  : [...DEFAULT_INPUT];
```

`defaultInputDeclared` 仍按「非空数组」判定，回退链优先级不变；把 schema 默认值
加回去（会重新短路兜底链）这条错误路线在注释里明确排除了。

真机验证（引擎 node 直接调 `resolveProfiles`）：

| 配置形态 | 修复前 | 修复后 |
| --- | --- | --- |
| `defaultInput: []` | 抛错，保存失败 | 不抛错，模型 `input=["text","image"]` |
| 未声明 | 不抛错，`["text","image"]` | 同左 |
| `defaultInput: ["text"]` | — | `["text"]`（用户声明优先，不被放宽） |
| `defaultInput: ["text","image"]` | — | `["text","image"]` |

## 2. LibreOffice：容器内原生无头版接入

### 为什么不能直接开 kit 的原生后端
`libreoffice-kit` 的原生后端要三样东西，Android 一样都没有：

- `@deepseek-ai/libreoffice-kit-<platform>` 引擎包。它只发布了
  `darwin-*` / `win32-*` / `linux-*-glibc` / `wasm` 七个 target，
  `platformTarget()` 对 `android` 直接返回 `undefined`；
  实测 `npm view @deepseek-ai/libreoffice-kit-linux-arm64-glibc` → **404**。
- 包里的 `dsoffice` 助手二进制（`--input-bytes` / `--output-path` / `--format`
  自研协议），不是 `soffice` 命令行，源码不在本仓库。
- `readEngine()` 还会逐字段校验 `prebuilds.json`（`schemaVersion` / `status: built` /
  `platform` / `glibcMinimum`），伪造一份出来只会在第一次转换时炸。

所以「把 `backend` 硬写成 `native`」是假装修好——请求期照样走 WASM。

### 实际做法（`patchLibreOfficeKitGlibcNative`）
真正能落地的是**把原生 LibreOffice 放进已有的 glibc Python 容器**（proot 里跑
未改动的 Ubuntu 24.04），再让 kit 在转换时走它：

1. `discoverRuntime()` 在 Android 上先探测
   `<root>/extensions/glibc/bin/kxxy-glibc` 与
   `<files>/glibc/rootfs/usr/bin/soffice`；
   都存在就报告 `backend: "native"`（`nativePreview` 仍是 `false`：
   **实时预览**依旧由内置 WASM 渲染器出图，只有文档转换走原生）。
2. 转换入口在 spawn 前插入原生分支：
   `kxxy-glibc -b <scratch>:<scratch> -- /usr/bin/soffice --headless --convert-to <fmt>`，
   输出经 `validateOutput()` + `pdfPageCount()` 校验。
3. 任何一步失败（版本不匹配、proot 起不来、输出非法）都**无缝回退**到原来的 WASM
   路径，并把失败原因写进日志；`KXXY_OFFICE_BACKEND=wasm` 可强制走 WASM。

容器内是 Ubuntu noble 的 `libreoffice-writer/calc/impress-nogui`（无 GTK/X 依赖），
装法见 `kxxy-glibc-provision libreoffice`。

## 3. 「预置」变成真的预置：装完扩展就自动跑一次离线预置

### 之前为什么 `.provisioned` 是空的
离线包一直随扩展下发（r4 起），但**预置动作**要等用户第一次敲 `julia` / `dotnet`
之类的垫片才触发。新装机的 `.provisioned/` 目录因此是空的——功能没错，语义不达标。

### 现在
`runInstall()` 收尾时（仅 `id === 'glibc'`、仅 Android）后台 `spawn` 一次

```sh
KXXY_GLIBC_OFFLINE=1 <ext>/bin/kxxy-glibc-provision offline-all
```

`offline-all` 依次做 julia / dotnet / wkhtmltopdf / python-ml / libreoffice，
每一项「已装即写戳走人」，所以重复触发是幂等的；全程零联网，缺包直接报错。
`KXXY_SKIP_AUTO_PROVISION=1` 可关掉。

扩展 r5 → **r6**，随包离线包从 3 个增到 5 个：

| 离线包 | 大小 | 用途 |
| --- | --- | --- |
| `julia-1.11.7-linux-aarch64.tar.gz` | 285 MiB | Julia 1.11.7 |
| `dotnet-sdk-8.0.404-linux-arm64.tar.gz` | 199 MiB | .NET SDK 8.0.404 |
| `wkhtmltopdf-noble-arm64-debs.tar.gz` | 91 MiB | wkhtmltopdf 0.12.6 |
| `python-ml-noble-arm64.tar.gz` | 103 MiB | 容器内 Python 3.12 + numpy/sklearn/cv2 |
| `libreoffice-noble-arm64-debs.tar.gz` | 168 MiB | 原生无头 LibreOffice |

池体积 628 888 438 → **912 961 303** 字节；新增两条命令 `soffice`、`libreoffice`
（同一个 `/usr/bin/soffice`，`libreoffice` 是习惯叫法）。

## 4. 顺带修的两处

- **`restamp-host-plugin.mjs --replace <entry>=<file>`**：换运行时里**单个上游文件**
  不必再全量重打 1.9 GiB。本次 pi-ai 的 3 行修复就是这么进去的（35 秒）。
  实现要点：额外替换**晚于**宿主树指纹计算再进替换集，否则 `kxxy-host/` 的
  内容指纹会与全量构建不一致，设备锚点 8 会判「指纹不符」无限重装。
- **`patchLibreOfficeKitGlibcNative` 的根目录回退**：`drawbridge` 从
  `lib/node_modules/@deepseek-ai/libreoffice-kit/lib` 往上退四级拿到的是 `lib/`，
  应为五级。真机上 `KXXY_ENGINE_ROOT` 恒由 `EngineConfig` 注入，所以功能不受影响，
  但独立调用 kit（脚本、测试）时会探不到容器。
- **能力探针补 `KXXY_ENGINE_ROOT`**：`office_engine` 原来裸跑 kit 的
  `capabilities --json`，进程里没有宿主注入的根目录，于是即便容器里已经装了
  LibreOffice 也只会报 `backend: wasm`。现在按 App 的真实契约传入
  `KXXY_ENGINE_ROOT` / `KXXY_FILES_DIR`，报出来的后端才与运行时一致。
