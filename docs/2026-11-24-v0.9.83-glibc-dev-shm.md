# v0.9.83：glibc 容器补上 `/dev/shm`，启动器自愈改成逐字节比对

日期：2026-11-24　产物：`dist/Kxxy-0.9.83.apk`　versionName `0.9.83` / versionCode `983000`

这一版只做一件事：**容器里的 `/dev/shm` 是空的**，于是 glibc 的 `shm_open()` /
`sem_open()` 无处落地，Python 的 `multiprocessing.SemLock`、`joblib`、`sklearn`
全都退回串行 —— 表面不报错，只印一行
`UserWarning: [Errno 2] No such file or directory … joblib will operate in serial mode`，
用户看到的是「并行慢得像单核」。

顺带把上一版留下的一个**判据缺陷**修掉：`healGlibcLaunchers` 原来靠「文件里含
`GUEST_ETC=`」判新版，这次不改成逐字节比对的话，已经装过 0.9.82 的设备会认为
启动器「已是最新」而跳过自愈 —— 也就是「装了新 APK，joblib 照样串行」。

---

## 1. 根因：Android 上没有可写的 `/dev/shm`

proot 把宿主 `/dev` 整体绑到 guest `/dev`（`-b /dev`）。Android 的 `/dev/shm`：

- 多数机型**根本没有这个目录**；
- 部分机型是 `/dev/shm → /dev` 的软链；
- 无论哪种，`untrusted_app` 域都写不进去。

glibc 从 2.34 起把 `/dev/shm` 当作 POSIX shm 的默认目录（`shm_open` / `sem_open`
落在那里），容器里这份 Ubuntu 22.04/24.04 正好是这个版本区间。目录不可用时
`sem_open` 返回 `ENOENT`，`multiprocessing.SemLock` 构造失败，joblib 捕获后降级为
串行 —— 这就是那行 Warning 的来历。`python3 -c 'import torch'` 之类不受影响，
所以之前一直没被当作「运行时缺件」。

## 2. 改法一：绑定一个 App 私有的 shm 目录

`tools/prebuilt/wrappers/kxxy-glibc.sh`，紧跟在 `-b /dev -b /proc -b /sys` 之后：

```sh
GUEST_SHM="$DATA/shm"
mkdir -p "$GUEST_SHM" || die "cannot create $GUEST_SHM"
chmod 1777 "$GUEST_SHM" 2>/dev/null || true
set -- "$@" -b "$GUEST_SHM:/dev/shm"
```

四个设计点：

1. **放在 `-b /dev` 之后不会冲突**。proot 对 bind 列表按 **guest 路径长度降序**匹配，
   `/dev/shm` 比 `/dev` 长，所以在 `/dev` 内部访问 `shm` 时命中的是这条私有目录，
   `/dev/null`、`/dev/urandom` 等其它节点仍然走宿主 `/dev`。顺序写成这样只是为了
   读起来与外层绑定相邻，proot 内部会重排。
2. **普通 ext4 目录够用**。glibc ≥ 2.34 不再校验 `/dev/shm` 的 `TMPFS_MAGIC`
   （早年 `shm_open` 要求 tmpfs，非 tmpfs 会 `EINVAL`），所以不需要真的挂 tmpfs，
   proot 里也挂不了。`chmod 1777` 只为语义正确（粘滞位），失败不致命。
3. **放 `$DATA/shm` 而不是 rootfs 里**。与 `$DATA/tmp`、`$DATA/etc` 同级；换 rootfs
   （`KXXY_GLIBC_ROOTFS`）或重装 glibc 扩展时，正在用的信号量不会跟着被删。
4. **`$DATA/shm` 里的残留不清理**。POSIX 命名信号量是持久文件，进程崩溃会留下
   `sem.*`；下次 `sem_open` 同名会打开它并沿用其值。这是 POSIX 的既有语义，
   Python 侧靠 `unlink` 自己收尾；容器退出时强删反而会让并发中的进程 `ENOENT`。

## 3. 改法二：自愈判据改成逐字节比对（不再维护特征串）

`RuntimeInstaller.healGlibcLaunchers()` 原来是：

```kotlin
if (readHead(it, 16 * 1024).contains(PYTHON_ROUTE_MARK)) continue   // "GUEST_ETC="
```

这个判据有结构性问题：**每改一次启动器就得记得同步推进那个常量**。这次正好撞上
——0.9.82 装过的设备两份启动器都带 `GUEST_ETC=`，只加 `/dev/shm` 不改判据的话，
自愈直接跳过，用户侧症状完全不变。

现在与 `ensureJvmWrappers` 同一套做法：把 APK 里的模板回填占位符，与盘上内容
**逐字节比**，不等就整份替换。

- 常量 `PYTHON_ROUTE_MARK`（`GUEST_ETC=`）→ `GLIBC_LAUNCHER_FEATURE`（`:/dev/shm`），
  语义从「判断文件是否最新」降级为「**校验模板本身是不是新的**」：拿旧模板去
  「修」会把两份启动器写回旧行为，比什么都不做更糟。以后模板再改，不必动这个常量。
- `PYTHON_ROUTE_PROBE_BYTES` 随之删除（没有调用者了）。
- 覆盖语义是对的：启动器是**随包分发的可执行文件**，不是配置。代价是手工改过它
  的人会被改回去 —— 接受。
- 保护面不变：只动「本来就存在」的两个路径（扩展没装时 ① 不凭空创建）；写临时
  文件再 rename（中断不留半个脚本）；读失败按「不等于」处理，写失败只记日志。

## 4. 连带：`runtime.zip` 里的那份必须同步重封

`verify-runtime.mjs` 会逐字节比对 `libexec/python-default/kxxy-glibc` 与源码，
不改运行时直接出包会被拦：

```
默认 Python/原生工具：✗ 路由未与当前源码同步：libexec/python-default/kxxy-glibc
结论：1 个关键条目缺失
```

所以先跑一次「只换一个条目」的重封（982 MB 全量重编不值得，其余条目原始压缩
字节整段搬运）：

```bash
node tools/sync-glibc-route-runtime.mjs \
  --in .cache/runtime-0.9.81/runtime.zip \
  --out .cache/runtime-0.9.83/runtime.zip \
  --meta android/app/src/main/assets/meta/build.json
```

结果：`6,931 B → 8,010 B`，未压缩字节 `+1,079`，`build.json` 的 `runtimeSha256`
跟着更新。

**这不会让老设备重解压 2.5 GiB**：`runtimeVersion` / 条目锚点都没变，`isComplete`
照样通过；设备侧的启动器由 §3 的 APK 资产自愈在启动快路径上覆盖。

### 构建机侧的参数装配验收

没有设备也能验「proot 到底收到什么参数」：用一个只 `printf` 的假 `proot` 顶掉
二进制，补齐 `rootfs/.kxxy-seed` 与 `bin/sh`，跑 `launcher.sh -c 'echo hi'`：

```
ARG[-b] ARG[/dev] ARG[-b] ARG[/proc] ARG[-b] ARG[/sys]
ARG[-b] ARG[<files>/glibc/shm:/dev/shm]
ARG[-b] ARG[<files>:/mnt/kxxy]
ARG[-b] ARG[<root>/etc/resolv.conf:/etc/resolv.conf]
ARG[-b] ARG[<root>/etc/hosts:/etc/hosts]
```

`/dev/shm` 那条夹在 `/dev` 与 `/mnt/kxxy` 之间，`$DATA/shm` 被创建；`sh -n` 语法检查
通过（`chmod 1777` 的粘滞位在 Windows 文件系统上看不出来，属于验证盲区）。

## 7. 未验证 / 风险（不要当成已通过）

- **没有装到任何设备**（本轮构建机侧 adb 无设备）。真机必须确认：
  ```sh
  kxxy-glibc -c "ls -ld /dev/shm && touch /dev/shm/x && rm /dev/shm/x"
  kxxy-glibc -c "python3 -W error -c 'import os; from joblib import Parallel, delayed; \
    pids = Parallel(n_jobs=2)(delayed(os.getpid)() for _ in range(4)); print(pids, len(set(pids)))'"
  ```
  期望：目录存在且可写；不再有 `joblib will operate in serial mode`；
  `len(set(pids)) >= 2`。
- 覆盖安装后**首次启动、不二次重启**：
  ```sh
  grep -c GUEST_SHM= $ROOT/extensions/glibc/bin/kxxy-glibc $ROOT/libexec/python-default/kxxy-glibc
  ```
  两份都要 ≥1（这是逐字节自愈的判据，0.9.82 的设备必须在这里被改掉）。
- **扩展池没重建**：`glibc.pool` 里那份 `kxxy-glibc` 还是旧的（无 `GUEST_SHM=`）。
  启动自愈会覆盖成新版；但「先装 APK、之后再在应用内装 glibc 扩展」这条路，要等
  下一次启动才会被修 —— 已登记为已知边界，没有在池子里重建。
- 如果设备上 `extensions/glibc` 本来就没装，① 不会被创建（按设计），只有 ② 被修好；
  装完扩展后下一次启动补上。
- `chmod 1777` 的粘滞位、以及「多进程共享同一份 `$DATA/shm`」只在真机上能验；
  Windows 上 `chmod` 是空操作，本地看不出差异。
- `poolSignature` 仍只比字节数（扩展池升级滞后那层未根治），与本轮无关。
