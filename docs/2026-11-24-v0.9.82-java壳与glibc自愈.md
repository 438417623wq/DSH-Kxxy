# v0.9.82：java 壳与 glibc 启动器两处回归修复

日期：2026-11-24　产物：`dist/Kxxy-0.9.82.apk`　versionName `0.9.82` / versionCode `982000`

这一版只做两件事，都是 v0.9.81 打完包之后才在设备侧暴露的问题：**PATH 上的
`java` 用不了**（连带 `d8`、`apksigner`），以及**升级后的第一次启动里 glibc 容器
的 DNS / localhost 仍然是坏的**。两处的根因都不是「代码没写」，而是判断依据选错
了：一个拿 `$0` 当文件位置，一个拿「扩展池那份」当权威内容。

运行时、扩展池、插件一字未动（`runtime.zip` 仍是 0.9.81 那份，sha256
`5a1d3a51…dd14`），所以这版**不需要重装 2.5 GiB 运行时**。

---

## 1. `java` / `d8` / `apksigner` 失效

### 根因

`RuntimeInstaller.jvmWrapperScript()` 生成启动器壳时，用 `$0` 推自己的目录：

```sh
d=${0%/*}; n=${0##*/}; r="$d/$n.real"
```

`$JAVA_HOME/bin/java` 这个入口是对的 —— gradle / mvn 直接 exec 它，`$0` 就是
本文件路径。但 `PATH` 上还有第二条入口：`<root>/bin/java` 是**指向**
`lib/jvm/<jdk>/bin/java` 的软链。经软链调用时 `$0` 是**软链的路径**，于是

```
d=<root>/bin  →  r=<root>/bin/java.real（不存在）
```

表现就是 `java: inaccessible or not found`。`d8`、`apksigner` 都是包一层 `java`
的垫片，一起哑掉，整条 APK 打包链在设备上断。`chmod 700 "$r"` 那行还先一步把
错误吞了，日志里只剩一句「文件不存在」。

### 改法

真身的绝对路径在写壳那一刻就是已知的（`real.absolutePath`），直接写死：

```kotlin
val data = jvmWrapperScript(name, real.absolutePath, prefix, flags)...
```

```sh
r='<root>/lib/jvm/<jdk>/bin/java.real'
[ -x "$r" ] || chmod 700 "$r" 2>/dev/null
exec "$r" -D… "$@"
```

`$0` 现在完全不参与定位：从软链、从 `$JAVA_HOME`、从相对路径调用都指向同一份
真身。比在壳里 `readlink -f` 少 fork 一次，也不依赖设备上有没有 `readlink`。
路径变了（换 JDK / 换引擎根）会让内容比对失败，`ensureJvmWrappers` 自动按新路径
重写，不会留下指向旧目录的陈旧壳。

存量设备不需要重装运行时：`ensureJvmWrappers` 在启动快路径上，按内容字节比对
决定是否重写，装上新 APK 首次启动即覆盖旧壳。

## 2. glibc 容器内 DNS / localhost 升级首启仍不可用

### 根因：时序倒挂

同一个启动器在设备上有两份：

- ① `extensions/glibc/bin/kxxy-glibc` —— 扩展池解出来的，`kxxy-glibc-provision` 调它；
- ② `libexec/python-default/kxxy-glibc` —— runtime.zip 里那份，裸 `python3` / `pip` 走它。

v0.9.81 的 `healPythonRouteScript()` 是「拿 ① 覆盖 ②」，并期望 ① 已经由扩展池
重装成新版。升级后的第一次启动上，这个期望不成立：

1. 引擎启动前（同步路径）：`ext-pool/glibc.pool` 还是旧文件 ⇒ ① 是旧的 ⇒ 没有
   可用的捐赠者，函数直接返回；
2. 引擎初始化：`kxxy-host` 跑 `extinstall.staleExtensions(root)`，它比的是
   「池体积 vs `.links.json` 里记的体积」，此刻两边都是旧值 ⇒ 判「已最新」不重装；
3. 引擎 Healthy 之后：`maintainAfterHealthy()` 才把新池拷进 `ext-pool/`，但
   `staleExtensions` 已经跑完、不会自己再跑一次；
4. 结果：整个会话两份启动器都是旧的 —— 容器内 DNS / localhost 照旧不可用，
   `kxxy-glibc-provision base`（调 ①）继续失败。用户看到的是「升了 APK 什么都没变」。

### 改法：判据换成 APK 自带的那份

新增 APK 资产 `assets/glibc-route/kxxy-glibc.sh`，构建期由
`tools/sync-glibc-route-asset.mjs` 从 `tools/prebuilt/wrappers/kxxy-glibc.sh`
**逐字节**同步（LF 归一化，与 runtime.zip / 扩展池同一套 `readScriptText`）。

`healPythonRouteScript()` → **`healGlibcLaunchers()`**：启动快路径上读这份模板，
按 `@DSH_ROOT@` / `@DSH_FILES@` 回填（与 `rewriteRootPlaceholder` 同一套规则），
**两份启动器一起写**，只写「盘上那份还不含 `GUEST_ETC=`」的目标。整个过程不依赖
扩展池重装、不依赖引擎、不等下一次启动。

为什么不从 `runtime.zip` 里抽 ②：`ZipFile` 只接受文件路径，而 asset 是流，抽一个
条目要先把 982 MB 的 zip 整份拷到 cacheDir —— 启动路径上不可接受。一个 6.9 KiB
的模板资产没有这个问题。

边界：盘上已带 `GUEST_ETC=` 就什么都不做（用户手改过也尊重）；文件不存在不动
（不负责创建，扩展没装时 ① 本来就不该有）；写 `.heal` 临时文件再 rename，中断不会
留下半个脚本。

### 没有动的那一层（留作后续）

`ensureExtensionPool` 拷完新池之后，`kxxy-host` 不会重新跑 `staleExtensions`，
所以**任何**依赖扩展池更新的扩展仍然要「多重启一次引擎」才生效。根治要么在
`kxxy-host` 里加一次复查/监听，要么给原生层一个通知通道 —— 两者都要改插件并
restamp 插件（`PATCHSET_MARKER` 跟着涨），本轮刻意不做：glibc 这条链路已经
由资产自愈覆盖，改插件会把「只改 Kotlin + 加一个小资产」的收益换成一个全量运行时
重封。

`poolSignature` 仍只比字节数（不比 hash），「改了内容而池体积恰好不变」仍探测不到；
记录为已知限制。

## 3. 防止再漂

- `tools/sync-glibc-route-asset.mjs [--check]`：同步/校验资产与源码。
- `tools/build-codex-apk.ps1` 在 `verify-runtime` 之后跑一次 `--check`，漂移直接
  拒绝出包（漂移的症状不是构建报错，而是「装上新 APK 后 DNS 依旧坏」，只能靠断言拦）。
- `tools/test-runtime-capability-contracts.mjs` 追加三条契约：
  1. APK 资产与源码逐字节一致、无 CR、含 `GUEST_ETC=`；
  2. `healGlibcLaunchers` 同时覆盖两份、且不再拿扩展那份当捐赠者；
  3. `jvmWrapperScript` 不出现 `${0%/*}` / `${0##*/}`，调用点传 `real.absolutePath`。

12 条契约测试全过。

## 5. 包内实际核对过的内容

- `assets/glibc-route/kxxy-glibc.sh`：**6,931 B，与 `tools/prebuilt/wrappers/kxxy-glibc.sh`
  逐字节相等**，CR 0 个，含 `GUEST_ETC=`。
- `classes*.dex`（9,239,516 B）含 `healGlibcLaunchers`、`glibc-route/kxxy-glibc.sh`、
  `extensions/glibc/bin/kxxy-glibc`、`libexec/python-default/kxxy-glibc`、
  `kxxy-jvm-launcher:`，以及新壳模板里独有的注释串（`# 不按 `、`绝对路径见下`）。
- dex 里仍有两处 `d=${0%/*}`，来自 `ensureDshWrapper`（写 `<root>/bin/dsh`）与
  `healPackagingWrappers`（恢复 `bin/pnpm` 等 corepack 垫片）—— 这两个目标都是
  `bin/` 下的**普通文件**、由用户直接 exec，`$0` 就是自身路径，语义正确；而且它们
  必须与 `build-runtime.mjs` 生成的内容逐字节一致，不能改成绝对路径。
- `verify-runtime` / `verify-python-repair` / `verify-startup-rescue-apk` /
  `verify-codex-apk` / `verify-python-apk` 全绿；`sign-apk --check` 指纹一致，
  `zipalign` 通过；`extensionPools: 33`。

## 6. 未验证 / 风险（不要当成已通过）

- **没有装到任何设备**（本轮构建机侧 adb 无设备）。以下必须在真机上确认：
  - `java -version`（走 PATH 的 `<root>/bin/java` 软链）有版本输出，
    `d8 --version`、`apksigner --version` 正常；
  - 覆盖安装后**首次启动、不二次重启**：
    `grep -c GUEST_ETC= $ROOT/extensions/glibc/bin/kxxy-glibc $ROOT/libexec/python-default/kxxy-glibc`
    两份都 ≥1；`kxxy-glibc -c "getent hosts localhost"` 返回 0；
    `kxxy-glibc-provision base` 能过 `apt-get update`。
- 若设备上 `extensions/glibc` 本来就**没装**，① 不会被创建（按设计），此时只有 ②
  被修好 —— 装完扩展后下一次启动补上。
- `healGlibcLaunchers` 只在启动快路径（`isComplete` 为真）与全量安装、维护阶段
  三处调用；若运行时被判不完整而走全量重装，本轮会先解压 2.5 GiB，那条路径上的
  自愈行为与 0.9.81 相同（模板来自 APK，不再依赖扩展）。
- 扩展池时序那层仍未根治（见 §2 末），`poolSignature` 仍只比字节数。
