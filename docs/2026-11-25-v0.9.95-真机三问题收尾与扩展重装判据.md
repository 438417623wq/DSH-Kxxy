# v0.9.95：真机三个问题的最后一道坎（扩展重装判据）

0.9.93 / 0.9.94 把三件事的**代码**都做完了，但真机（Redmi K60 Pro）上一直「没修好」。
本篇记录真机实测的结论、卡住的那一处、以及修法。

| 问题 | 0.9.94 状态 | 真机实测（本文） |
|---|---|---|
| ① 发图被拒 | 代码已改（补丁集 `@42`） | **已解决**：当前配置 `dhd` 与三条中转路由都放行，`o3-mini` 等已知纯文本仍拦 |
| ② LibreOffice 原生缺失 | 口径是「维持 WASM」，只补可查 | **已确认**：探针 `office_engine.backend = wasm`、`kit 0.2.3`、`pdfBackend = pdfium` |
| ③ glibc 工具要联网 | 三份离线包已在池里 | **此前根本没落盘**，本轮找到根因并修；离线从零装三件套 2 分钟 |

## 0. 先纠正一个前提：设备装的是 0.9.80

```
$ adb shell dumpsys package app.kxxy | grep versionName
    versionCode=980000 versionName=0.9.80
$ adb shell run-as app.kxxy cat files/engine/lib/node_modules/kxxy-host/patchset.version
kxxy-patchset@38
```

0.9.93 / 0.9.94 的产物只在 `dist/` 里，设备上一次升级停在 11 月 23 日。所以「三个问题一直
没修」的第一层原因就是：**修复没上机**。装 0.9.94 后（3.46 GB，2 分 40 秒；首启把运行时从
`@38` 解压到 `@42`，约 55 秒）①② 立即生效，③ 仍然不行 —— 于是有了下面这条真 bug。

## 1. ③ 的真正根因：`.links.json` 把「新池体积」记在「旧池内容」上

设备上的 glibc 扩展重装过，但内容是旧的：

```
$ run-as app.kxxy ls -l files/engine/extensions/glibc/bin/
-rwxr-xr-x kxxy-glibc-provision   6875   ← 新版是 14235 字节，且没有 KXXY_GLIBC_OFFLINE
$ run-as app.kxxy cat files/engine/extensions/glibc/.ext-version
24.04.3-r4
$ run-as app.kxxy grep poolBytes files/engine/extensions/glibc/.links.json
  "poolBytes": 628888438              ← 这是 r5 池的体积（r4 池约 40 MB）
$ run-as app.kxxy ls files/engine/extensions/glibc/provision   → 不存在
```

池是对的（`glibc.pool` 11 个条目，含 julia 299 MB / dotnet 208 MB / wkhtmltopdf 95 MB），
但**扩装时读的是旧池**。时序：

1. 引擎启动（20:47:24），kxxy-host 插件跑 `staleExtensions()` —— 老扩展 `layout` 落后，
   判定要重装，`startInstall()` 立刻开工，打开的是**旧池**的文件描述符（8 个条目，1 秒解完）；
2. `RuntimeInstaller.ensureExtensionPool()`（健康后的异步维护）用 `.part` + rename 把
   **新池**（628 MB）原子替换到位；
3. `buildViews()` 收尾时 `poolSignature(root, id)` 按**路径**重新 stat ⇒ 记下新池体积。

于是 `.links.json` 声称「我用的是 628888438 字节的池」，而目录里是旧内容。
`staleExtensions()` 的两条判据（`layout`、`poolBytes`）从此都判「最新」，**这台设备再也不会
重装 glibc** —— 离线包一个也落不下来，而池体积此后不再变化，光看体积永远发现不了。

### 修法（`plugins/kxxy-host/lib/extinstall.mjs`）

1. **解包前后各 stat 一次**：池体积变了就是「池在解包途中被换掉」，删掉临时目录重来
   （最多一次；再变就报 `pool replaced during extract`，不再写出一份骗人的清单）。
2. **`poolBytes` 取解包前量到的值**：`buildViews(root, id, extDir, { poolBytes })`，
   记录的一定是**真正消费过**的那个池。
3. **`staleExtensions()` 增加版本判据**：`.ext-version`（目录里写的）与
   `extensions.json`（随包目录的）不一致就是落后 —— 体积恰好没变、或体积被记错时，
   这是唯一能发现问题的信号。只比两边都非空且非 `unknown` 的值，避免把老扩展
   （没写过版本戳）判成「每轮都重装」。

回归：`node tools/test-extinstall.mjs` → **155 通过 / 0 失败**（新增 4 条：池体积一致但
版本落后要重装、版本一致不重装、`unknown` 不判落后、没有 `.ext-version` 不判落后）。

### 还有一处产物不一致

0.9.94 的运行时（sha `f6df34bb…`）是 0.9.93 那份，里面 `kxxy-host/extensions.json` 仍写
`glibc 24.04.3-r4`，而 ext-pool 里的池已经是 r5：

```
device: {"id":"glibc","version":"24.04.3-r4","sizeBytes":632832668}
repo  : {"id":"glibc","version":"24.04.3-r5","sizeBytes":632835729}
```

**池重建了、随包的目录清单没跟着重建**，于是「版本判据」在 0.9.94 上也救不了场（两边都是 r4）。
0.9.95 用 `tools/restamp-host-plugin.mjs` 把 `plugins/kxxy-host/` 整体重封进运行时
（`kxxyHostFingerprint e36d3a89… → 55f4dad9…`，运行时 sha `dde97496…`），两处对齐。

补丁集仍是 `@42`（运行时内容变了，但补丁集标记管的是「要不要重解压」，这里只换插件，
设备靠 `kxxyHostMarker` 重装插件，不必重解压 2.5 GB）。

## 2. ① 图片：真机上把判定链跑了一遍

`resolveRouteModels()` 没有导出，验证方式是：在同目录复制一份 `index.js` 补一行
`export { resolveRouteModels }`，用**引擎自己的 node** 跑设备上那份字节（不是另抄一份逻辑）：

| 路由 | 结果 |
|---|---|
| 当前配置 `dhd` / `openai-completions` / `deepseek-ai/DeepSeek-V4.1-Flash` | `["text","image"]` ✓ |
| 中转 `guiji` / `openai-completions` / `gpt-4o` | `["text","image"]` ✓ |
| 中转 `chat` / `anthropic-messages` / `claude-sonnet-4-5` | `["text","image"]` ✓ |
| 中转 `guge` / `google-generative-ai` / `gemini-2.5-pro` | `["text","image"]` ✓ |
| 未知中转 `openai-completions` / `some-relay-model-x` | `["text","image"]` ✓（协议兜底） |
| 已知纯文本 `o3-mini` / `openai-responses` | `["text"]` ✓（`knownTextOnlyModel` 拦住） |
| 用户显式写 `input: ["text"]` | `["text"]` ✓（显式优先） |
| 非对话协议 `openai-embeddings` | `["text"]` ✓ |

**仍未验证**：上游是否接受图片。本地两道门都过了，但中转/模型是否 400 只有真发一次才知道。
另注意 `deepseek-ai/DeepSeek-V4.1-Flash` 现在走的是「目录规范化 id 命中」那条回退
（拿到 `ctx=1048576`、`max=32768`），如果上游其实是纯文本模型，症状会从「本地拒绝」
变成「请求期报错」——这是本次改动的已知代价，取舍见 0.9.94 文档。

## 3. ② Office：后端已可查，仍是 WASM

探针（`tools/probe-runtime-capabilities.py`）在设备上直接跑 Kit 自己的命令：

```
office_engine: pass
  kitVersion 0.2.3   backend wasm   native false   pdfBackend pdfium
  note: WASM engine: conversion works, desktop-exact layout is not guaranteed
```

顺带修了探针一个**只有真机才暴露**的缺陷：bionic 的 CPython 没有 `os.link`
（`AttributeError: module 'os' has no attribute 'link'`），原来直接把整份报告打崩，
而不是报「没有硬链接能力」。现在 `os_link()` 走 `ctypes` 调 `link(2)` 兜底，
外层再兜 `AttributeError` —— 探针在任何平台上至少能出报告。

设备探针结果：`pass 9 / fail 2（ln、rsync —— 应用域 EACCES 是已知策略边界）/ skip 2`，
`office_engine` 与 `native_python3` 都 pass。

## 4. ③ 验收：断网（严格离线）从零装三件套

先删掉容器里的 julia / dotnet / wkhtmltopdf 与对应标记（模拟新装机第一次用），再
`KXXY_GLIBC_OFFLINE=1` 预置 —— 该开关下 apt / pip / 官方 tarball 全部被拦，只能走随扩展的本地包：

```
== 安装 Julia 1.11.7（离线包，约 285 MiB）==      julia 1.11.7
== 安装 .NET SDK 8.0.404（离线包，约 200 MiB）==  8.0.404
== 安装 wkhtmltopdf 0.12.6 + 依赖（离线包）==     wkhtmltopdf 0.12.6
rc_provision=0        （21:02:48 → 21:04:54，2 分 06 秒）

julia version 1.11.7 / 8.0.404 / wkhtmltopdf 0.12.6
provision/ 目录：装成功后按设计删包（total 0，省 580 MiB）

== 负向分支 ==
kxxy-glibc-provision: KXXY_GLIBC_OFFLINE=1，但 apt 源（base）需要联网
  → 离线模式只走随扩展的本地包（julia / dotnet / wkhtmltopdf 三个）。
rc_base_offline=1
```

注意 `dotnet` 从原来的 `8.0.134`（容器里 apt 装的）变成官方 SDK `8.0.404` ——
离线包是微软官方 tarball，不依赖 ubuntu 源版本。
