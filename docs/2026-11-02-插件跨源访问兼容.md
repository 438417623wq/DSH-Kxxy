# 插件面板打不开：跨源策略与「Failed to fetch」

> 2026-11-02 · 对应版本 0.9.10
> 现场：`billion-context`（上下文压缩代理）安装后，面板显示
> 「连接 bili 代理失败」，错误文本是
> `Failed to fetch (http://127.0.0.1:18787/__bili/?embed=1)`

## 一、先排除「代理没起来」

这段报错极易被读成「插件没跑起来」，实际不是。证据在插件的服务端：

```js
// billion-context/dist/agent/dsh-native.js
const originRoute = {
  kind: 'exact',
  path: '/bili/origin',
  handler: (_req, res) => {
    const origin = currentOrigin()          // ← register.base
    const body = JSON.stringify(
      withCtxTabFace(
        origin !== undefined && adminRelayEnabled()
          ? { origin: null, relay: true }   // 只有开了 adminRelay 才走这个分支
          : { origin: origin ?? null },
      ),
    )
    res.writeHead(200, { 'content-type': 'application/json' })
    res.end(body)
  },
}
```

`currentOrigin()` 返回的 `register.base` 只有一个来源 —— `bootstrap()` 里的

```js
const handle = await ensureProxyRunning({ host, port: 0, lane: 'dsh' }, { scriptPath })
register.base = handle.origin        // ← 形如 http://127.0.0.1:18787
```

也就是说：**设备上 `/bili/origin` 返回了 `18787`，说明 `ensureProxyRunning`
已经成功、lane 已经监听**。代理是活的，坏的只是「页面读不到它」。

## 二、真正的拦截点：浏览器同源策略

插件前端要读的是**另一个端口**：

```
宿主页   http://127.0.0.1:3080     ← DSH 官方前端
请求目标 http://127.0.0.1:18787    ← 插件自己的代理
```

端口不同即跨源。而这条服务**不返回任何 CORS 响应头** —— 我把
`dsh-native.js` 全文件搜了一遍，`Access-Control-Allow-Origin` 只出现在内联的
undici header 白名单里，没有一处是真正设置响应头。

那桌面端为什么没事？因为桌面端跑在 Electron 里，渲染进程默认那套策略与
浏览器的「严格同源」不同（DSH 主进程还放宽了 web 偏好）。Android 的 WebView
**强制执行同源策略，而且没有任何开关能关掉** —— 不存在 `webSecurity: false`
对应的 API。于是同一行 `fetch` 移植过来必然抛：

```
TypeError: Failed to fetch
```

这个报错文本是浏览器在「响应被 CORS 丢掉」时的统一说法，与「连不上」在
JS 层**不可区分** —— 这正是它在真机上特别难判断的原因。

## 三、修法：在服务端补一个头

```
android/app/src/main/assets/guard/kxxy-cors.cjs
```

通过 `NODE_OPTIONS=--require` 注入（和 `kxxy-guard.cjs` 同一套机制），
包装 `http.Server.prototype.emit` 的 `request` 事件：

| 场景 | 行为 |
|---|---|
| 带 `Origin: http://127.0.0.1:*` / `localhost` / `[::1]` | 回显 Origin + `Allow-Credentials: true` + `Vary: Origin` |
| 不带 Origin（同源请求，绝大多数流量） | 一个头都不加 |
| Origin 是外部网站 | 不回显 |
| `OPTIONS` + `Access-Control-Request-Method` | 直接 204 应答，且**不再往下传** |

三个设计取舍值得记下来：

**① 为什么回显 Origin 而不是发 `*`。**
插件面板要带凭证，`*` 配 `Allow-Credentials: true` 会被浏览器直接拒绝。
同时只回显回环 Origin，顺手挡住了「外部网页读本机端口」—— 18787 里存着
上游 API Key 与完整对话，那条路不能开。

**② 为什么补在引擎侧，而不是 WebView。**
WebView 没有「关同源」的 API。`shouldInterceptRequest` 转发看似可行，但它要求
每个请求都走一次 Java → 网络 → Java 的往返，而且插件面板大量使用 SSE 与
长连接，透传要在 Java 层重新实现 —— 一处没做对就是新的白屏。
反过来，插件的 HTTP 服务**全都跑在这个 Node 进程树里**，加个头就完事，
而且对「以后任何插件起的本地服务」一并生效。

**③ 为什么预检要吞掉请求。**
预检到达时业务 handler 还什么都没做；让它继续跑只会对着已发送的 204 再写
一次，日志里多一条 `ERR_HTTP_HEADERS_SENT`。`emit` 返回 `true` 且不调原始
emit，就能干净地截住。

## 四、子进程必须也装上

lane 是 **spawn 出来的独立进程**（`spawnImpl(runtime, [script, 'start', ...])`），
只在主进程装没有任何意义。注入走 `NODE_OPTIONS`，而子进程继承它 —— 这一点
不能想当然，我核对了上游的 spawn 环境：

```js
env: {
  ...stripInheritedProxy(process.env),          // 只删 HTTP_PROXY 等代理变量
  ...captureInheritedProxyEnv(process.env),     // 只搬 BILI_INHERITED_* 快照
  ...(process.versions.electron ? { ELECTRON_RUN_AS_NODE: '1' } : {}),
  BILI_LAUNCH_TOKEN: launchToken,
  ...
}
```

`stripInheritedProxy` 删的是 `INHERITED_PROXY_VARS`，`stripInheritedLauncher
Channels` 删的是 5 个 `BILI_*` 通道 —— **`NODE_OPTIONS` 原样传下去**，
补丁在 lane 里同样生效。

与 `kxxy-guard.cjs` 的关键差异：guard 有 `KXXY_GUARD_MAIN=1` 只让主进程装
（否则插件跑 `npm install` 时会吞掉致命错误），**cors 没有这个开关** —— 它
恰恰需要装进子进程。代价是它会被装进每一个 node 子进程，所以整份逻辑包在
`try/catch` 里，任何一步失败都静默放过：注入失败只是少一层兼容，绝不能让
引擎起不来。

## 五、验证

**单元（`node tools/test-cors-shim.mjs`，22 项全绿）**

契约层，用 Node 的 http 客户端看原始响应头：回显本机 Origin、同源不加头、
外部 Origin 不回显、预检 204 且 handler 不执行、SSE 三块数据齐且带头、
双层 `--require` 幂等、`KXXY_CORS=0` 可关。

**浏览器（`node tools/verify-cors-browser.mjs`）**

Node 客户端不执行同源策略，只能证明「头发出去了」，证明不了「浏览器放行」。
所以另起一台真 Chromium，两个回环服务分别占 3080 / 18787，跑同一段 fetch：

```
装补丁  : OK text/html; charset=utf-8
不装补丁: ERR TypeError: Failed to fetch
```

对照组报的**正是用户截图里那句** —— 根因与修复都被这条对照钉死了。

## 六、边界

- **远程访问场景没覆盖**：从局域网 IP 打开控制台时，Origin 是
  `http://192.168.x.x:3080`，按上面的策略不回显。那种场景应当让插件走它自己的
  relay 模式（`security.adminRelay: true`，服务端会把 `/__bili` 反代到宿主
  端口上，天然同源）。默认不做，是因为那会把本机端口暴露给整个局域网。
- **`ws://` 不走这条补丁**：跨源 WebSocket 本身不受 CORS 约束（服务端可以
  自选是否校验 Origin），不需要处理。
- **`KXXY_CORS=0`** 可整机关掉，排查「是不是它干的」时不用改代码。
