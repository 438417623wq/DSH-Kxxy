# 内置 DSH 更新：验收与日志归档

每次更换内置 DSH、重打 runtime 或修复覆盖升级问题，都在 `docs/dsh-upgrades/v<APK版本>/` 留一份**可提交的脱敏记录**，并在本页加索引。成功和失败都留；不能只在构建机的 `.cache` 里留日志。下一次从最近一份记录和上一版正式 APK 开始，不从目录名或旧缓存猜基线。

## 每次更新都要带回来的证据

1. **记录输入。** 从旧、新 runtime 内读取 `lib/node_modules/@deepseek-ai/dsh/package.json`；记录实际版本，以及所用 ASAR 的来源、版本、SHA-256（未用/未知则明说）。记录发布 APK、内嵌 runtime、基线宿主指纹、补丁集与扩展池清单。不能用工作区 `HEAD` 或文件时间代替发布物摘要。
2. **保留第一处失败。** 写下症状、失败命令、错误原文、根因和修法。把状态区分为通过、失败、缺夹具未执行、未做真机验收。保留改前的反例和改后的同一项断言；不要只摘最后的 `PASS`。
3. **分开验证新装、覆盖升级、真机。** 在隔离工程里跑 runtime、修复包和安装路由校验；用正式旧包跑 JVM 迁移，检查冲突零写入、文件保留、第二次零替换。功能有改动时要实跑消费者：字体用 `FcFontList` 和生成的 PDF，不能仅用 `fc-match`。有条件时另存 Android 上的启动、预置和转换结果，未测就写未测。
4. **验证最终 APK。** 从签名后的 APK 而不是暂存目录读取版本、runtime、启动器和池；核对签名、SHA-256 和预期未变化的条目。在对应版本目录保留报告与必要的日志原文摘录。
5. **归档到 GitHub。** 单独审查待提交的文件和差异，确认远端、分支及可见范围。只上传本轮记录与脱敏报告；不要上传原始会话、用户文档、环境变量、账号令牌、设备序列号、绝对路径、签名材料、ASAR、APK、runtime 或整个 `.cache`。记录提交和可访问的链接；未推送或推送失败就明确写出来，不算归档完成。
