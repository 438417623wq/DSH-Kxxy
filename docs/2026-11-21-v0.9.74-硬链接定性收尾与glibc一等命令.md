# v0.9.74：硬链接定性收尾，glibc 工具升为一等命令

> 这一版处理三件事：把「硬链接建不出来」从「反复怀疑」变成**有完整取证的定论**，
> 并让所有相关命令在退化时说清原因；把 julia / dotnet / wkhtmltopdf / python-ml
> 从「进容器才会用」变成**装完就能敲的普通命令**；给 `perf` 一个同样有取证的结论
> ——这条是真做不到，不是没做。

## 1. 硬链接：取证矩阵与最终定性

先把「是不是文件系统 / 是不是权限位 / 是不是跨挂载」全部排除掉，再下结论。
探针用 `ctypes` 直调 libc（该设备的 CPython 未编译 `os.link`），逐个目录跑：

| 路径 | `link(2)` | `linkat(0)` | `rename` 对照 |
| --- | --- | --- | --- |
| `files/hlprobe` | rc=-1 errno=13 **EACCES** | rc=-1 errno=13 **EACCES** | ok（dev 65060 / ino 2948315） |
| `cache/hlprobe` | rc=-1 errno=13 **EACCES** | rc=-1 errno=13 **EACCES** | ok（dev 65060 / ino 2948195） |

- `EACCES` 而不是 `EPERM`：排除 `fs.protected_hardlinks`（那条只会回 EPERM）。
- 同目录 `rename` 成功 → 不是挂载只读、不是 quota、不是 inode 耗尽。
- 同进程 `symlink(2)`、`open(O_CREAT)` 均成功 → 不是文件描述符/权限位问题。
- 进程域：App 内 `u:r:untrusted_app_27:s0`；`run-as` 下 `u:r:runas_app:s0:c142,...`。
  两者都被摘掉了 `file link` 权限。
- **关键对照**：连 `u:r:shell:s0`（adb shell，权限远高于应用）在 `/data/local/tmp`
  上建硬链接同样是 `EACCES`。所以这不是「我们这个 App 的特殊待遇」，是设备策略。

结论：`/data` 是 f2fs + `seclabel`，`link(2)` / `linkat(2)` 被 LSM 拒，
**改 sepolicy 要 root，用户态无解**。`st_ino` 相同的硬链接在这个设备上永远做不到；
`rsync --link-dest`、`cp -l`、`git worktree` 的共享对象随之一并不可用。

### 既然建不出来，工具要「说实话」

三条命令的行为在这一版被固化成显式契约，而不是静默退化：

| 场景 | 行为 |
| --- | --- |
| `ln a b` | 建**绝对路径符号链接**（同一份数据、不额外占空间、改一处两处都变），stderr 说明原因 |
| `KXXY_LN_STRATEGY=copy` | 退回独立副本（需要能独立修改副本时用），并提示「改一处不会同步」 |
| `KXXY_LN_STRICT=1` | 直接失败并打印原因，不建任何文件（要确认「真的建不了」时用） |
| `KXXY_LN_QUIET=1` | 关掉那行说明（脚本里要干净输出时用） |
| **`kxxy-rsync --link-dest`** | 提示「将退化为整份复制」（rsync 自己会静默复制，退出码 0） |
| `KXXY_RSYNC_LINK_STRICT=1` | 直接失败，并建议改用 `--copy-dest` |

`kxxy-rsync` 刻意**不**自动把 `--link-dest` 改写成 `--copy-dest`：后者取文件的来源
不同（从 dest 本地取），而用户脚本里的 `--link-dest` 通常还配合 `--delete` 做轮转，
偷偷换参数比说一句真话更容易埋雷。

为什么包装器叫 `kxxy-rsync` 而不是直接盖掉 `rsync`：`bin/rsync` 是 shells 扩展池
装进来的，扩展重链（`relinkAll`）要在 `bin/` 下建同名软链；运行时就占住这个名字
会让那条链接建不出来，等于把真 rsync 弄丢。宁可多一个名字，不能弄坏主体。

## 2. julia / dotnet / wkhtmltopdf / kxxy-py：升为一等命令

上一版（v0.9.73）能把 Ubuntu 跑起来，但用法是 `kxxy-glibc -c '...'`——「能跑」
和「能用」之间还差一层。这一版把四个最常被要的工具做成**装完即用**的命令：

```
julia --version        # 1.11.7
dotnet new console     # 8.0.134
wkhtmltopdf in.html out.pdf
kxxy-py -c 'import sklearn, cv2'
```

每个命令都是几十行的 `/system/bin/sh` 垫片（模板：`tools/prebuilt/wrappers/glibc-tool.sh`），
逻辑只有三条：

1. 容器里已经有这个可执行文件 → 直接 `exec kxxy-glibc -- <exe> "$@"`；
2. 没有 → 先跑 `kxxy-glibc-provision <group>`（幂等，带进度），成功后重试；
3. `KXXY_GLIBC_NO_AUTO=1` → 只报「先执行 kxxy-glibc-provision xxx」，不自动下载。

预置逻辑在 `kxxy-glibc-provision`：apt 走 `-o APT::Sandbox::User=root`（fake root 下
`_apt` 用户不存在），julia 走官方 aarch64 tarball 解到 `/opt/julia-1.11.7`，
python-ml 走 `pip --break-system-packages` 装 manylinux 轮子。每个目标成功后
在 `<files>/glibc/.provisioned/<group>` 留标记，装过一次就跳过。

这条路径的实际价值：在 bionic 侧「只能 NDK 交叉编 40+ 扩展」的 sklearn/cv2，
在这里就是一条 `pip install`。

## 3. `perf`：取证后确认做不到

不是「索引里没有」这么简单，这一版把三条路都试完：

| 尝试 | 结果 |
| --- | --- |
| Termux `linux-perf` | 索引里没有（只有 `gperf`/`hyperfine`/`iperf3`） |
| NDK `simpleperf stat -e cpu-cycles:u -- <cmd>` | `workload.cpp:36] Running child command in app uid isn't allowed.` |
| NDK `simpleperf record -e ...` | `environment.cpp:340] Failed to SetProperty debug.perf_event_max_sample_rate` |
| 进 glibc 容器 | 一样：`perf_event_open` 在应用域被拒，容器不改域 |

`perf_event_open` 属应用域被显式摘掉的权限，且系统属性不可写，所以采样型性能剖析
在本 App 内不可提供。可用的替代（已具备）：

- 用户态耗时剖析：`valgrind --tool=callgrind ./prog`（valgrind 扩展池）
- Node：`node --cpu-prof`；Python：`python -m cProfile`
- 粗粒度：`time`、`ps`、`/proc/<pid>/status`

## 4. 真机验收（Redmi K60 Pro / Android 13 / patchset 31）

| 项 | 结果 |
| --- | --- |
| `ln a b` | 建软链（`l` 位、指向绝对路径），stderr 说明 SELinux 原因 |
| `ln -f a b` / `ln -T a b` | 同样建软链（缺陷 EB：旧版把 `-f` 当成源，`$# > 2` 判定直接失败） |
| 多源落目录 `ln a b dir/` | `dir/a`、`dir/b` 两条软链 |
| `KXXY_LN_STRICT=1 ln a b` | rc=1、不建文件、打印 `link(2) -> EACCES` |
| `kxxy-rsync --link-dest` | 打印退化提示后正常完成复制（不进 strict） |
| `KXXY_RSYNC_LINK_STRICT=1` | rc=1，提示改用 `--copy-dest` |
| 扩展中心安装路径（`startInstall`） | 随包 `glibc.pool` → `done 100%：8 个文件，6 个命令接入，回填 6 个` |
| `julia --version` | `julia version 1.11.7` |
| `dotnet --version` | `8.0.134`（`dotnet new console` + `run` → Hello, World!） |
| `wkhtmltopdf --version` | `0.12.6`，HTML→PDF 真渲染（输出头 `%PDF-`） |
| `kxxy-py -c 'import numpy,sklearn,cv2'` | 2.5.5 / 1.9.1 / 5.1.0 |
| 首跑预置幂等 | 第二次直接跳过（`.provisioned` 标记命中） |
| `KXXY_GLIBC_NO_AUTO=1`（容器里没装时） | rc=127，提示 `kxxy-glibc-provision <group>`，不联网 |

## 5. 代码落点

- `tools/prebuilt/wrappers/glibc-tool.sh`（新）：垫片模板，`__NAME__/__EXE__/__GROUP__`
  等令牌在构建期渲染。
- `tools/prebuilt/wrappers/kxxy-glibc-provision.sh`（新）：幂等预置脚本。
- `tools/lib/asset-pack.mjs`：支持 `toolTemplate` + `tools[]` 批量渲染垫片，并与
  `bins` 交叉校验（声明的命令必须都产出，避免「卡片说有、装完没有」）。
- `tools/lib/seeds.mjs`：glibc 条目升到 `24.04.3-r2`，`bins` 列出六个命令；
  dotnet 条目注记改为「走 kxxy-glibc」。
- `tools/build-runtime.mjs`：新增 `rsyncWrappers()`（`bin/kxxy-rsync`）；
  `ln` 的位置参数改为单独计数（缺陷 EB：`ln -f a b` 的 `$#` 是 3，旧的
  「多源落非目录」判定会把它误判成错误并 rc=1 —— 真机表现是「什么都不建、
  只回一行 coreutils 的 Permission denied」）；
  临时 spill 文件的清理改为 `dropSpill()` —— 构建机的删除钩子会把 600 MiB
  临时文件搬进回收站再报 `参数错误 (0x80070002)`，把构建打断在半路，
  现在改为「删不掉就 truncate 到 0」，不依赖删除成功。
- `tools/build-apk.ps1`：池目录改为**按文件合并**（缺陷 EA，见 §6 第 6 条）。

## 6. 已知限制

1. **硬链接**（含 `st_ino` 相同）不可得，`rsync --link-dest` / `cp -l` / `git worktree`
   的去重语义永远达不到。`ln` 与 `kxxy-rsync` 只保证「说清原因 + 可选的严格失败」。
2. **`perf` 不可得**（见 §3）。
3. 容器内工具比原生慢 2–5 倍（每条 syscall 多一层 ptrace 转发）；julia/dotnet 的
   启动延迟里还含着 `kxxy-glibc` 进入容器的固定开销（约 0.3–0.6 s）。
4. 四个垫片命令依赖 glibc 扩展；扩展未装时是 `127 + 明确提示`，不是静默失败。
5. 首次预置需要联网，julia 约 285 MiB、dotnet 约 200 MiB、python-ml 约 120 MiB。
6. **从 v0.9.73 升上来的用户要重装一次 glibc 扩展**才会拿到四条新命令：
   `extensions/glibc/.links.json` 记的是安装当时的 `bins`（那时只有 `kxxy-glibc`），
   `relinkAll()` 只按这份记录重建链接。扩展中心点一次「更新/重装」即可。
   （手工把池解到目录、不写 `.links.json` 的安装方式同理，而且升级 APK 后
   `bin/` 里的链接会消失 —— 本次验收就是先把 `extensions/glibc` 删掉、
   走真实的 `startInstall()` 装了一遍才验证的。）
