# v0.9.73：glibc 用户态扩展（proot + Ubuntu 24.04 base）

> 上一版（v0.9.72）把「硬链接建不出来」定成了不可解的内核/SELinux 事实。这一版不再
> 跟它较劲，改为绕过去：把「只有 glibc 构件」的那一整类工具，交给一份**未改动的
> Ubuntu 用户态**去跑。用户此前提的四项遗留里，julia / dotnet / wkhtmltopdf /
> sklearn / cv2 全部因此可用。

## 1. 为什么是「用户态」而不是「再补几个 bionic 包」

v0.9.68–v0.9.72 一路补下来，工具缺口已经不在「索引里有没有这个包」，而分成两类：

| 类型 | 例子 | 能不能用 Termux deb 解决 |
| --- | --- | --- |
| 上游按 bionic 交叉编译 | flang、zig、deno、texlive | 能，补依赖即可（v0.9.72 的 flang 修法） |
| **上游只有 glibc 构件** | julia、dotnet host、wkhtmltopdf、PyPI 的 manylinux 轮子（sklearn / cv2） | **不能**，索引里根本没有 |

第二类的处置在 v0.9.69 已经被迫做过一次（`dotnet` 先发包后撤回、`sklearn` 归因为
「只能 NDK 交叉编译」）。这一版换路子：**不在 bionic 上解决它，而是给一个 glibc 世界**。

proot 用 ptrace 做路径/系统调用转译，不需要 root、不加载内核模块、不改系统分区，
在同一个 uid 里就能跑一份完整 Ubuntu 用户态。代价是每条 syscall 多一层转发。

## 2. 池子的第三种来源：`asset`

在此之前扩展池只有两种来源，都建立在「上游按包分发、我们解包重排」之上：

| 来源 | 实现 | 输入 |
| --- | --- | --- |
| deb | `tools/lib/poolextract.py` | Termux 索引求闭包 → 解 `data.tar.xz` |
| npm | `tools/lib/npm-pack.mjs` | registry tarball → 三平台过滤 |
| **asset** | `tools/lib/asset-pack.mjs`（本版新增） | **整块资产 blob + 包装器模板** |

glibc 要带的东西不在前两个世界里：一份 Ubuntu base rootfs，只有一个 30 MB 的
`.tar.gz`，没有 deb 索引、没有依赖图、也不该被解开重排。

产物与另两种来源**逐字节同构**，`extinstall` 不需要新分支：

```
<id>.pool                  tar.gz，路径相对扩展目录
bin/<cmd>                  包装器（含 @DSH_ROOT@ 等占位符，装完回填）
rootfs/ubuntu-base.tgz     整块资产（不透明 blob）
.pool-manifest.json        列出待回填的文本文件（只有包装器）
```

### 2.1 为什么不把 rootfs 解成文件树

设备端的池解包器是 `plugins/kxxy-host/lib/tar.mjs`，它对符号链接的策略是
**跳过并记账**（池里的软链一律由构建期物化成实体副本）。rootfs 里那 194 条软链
（`/bin -> usr/bin`、`/lib -> usr/lib`、`/usr/bin/awk -> mawk`…）一旦被物化成副本，
`/lib/aarch64-linux-gnu/libc.so.6` 与 `/usr/lib/aarch64-linux-gnu/libc.so.6` 就成了两份
互不相干的文件 —— apt 换 glibc 时必然撕裂，ld.so 缓存也会指错。

所以 rootfs 当**不透明 blob** 进池，由 `bin/kxxy-glibc` 首次运行时用设备上的 GNU tar
解开（软链、权限位、目录顺序全交给 tar），构建期不碰。

### 2.2 构建期唯一的改写：去掉硬链接

归档里带硬链条目 = 解到那儿必失败（`link(2)` → EACCES，v0.9.72 已定性）。
`tools/lib/tarderef.py` 把硬链条目改写成独立副本（**不碰软链**），产物零硬链，
设备端 `tar -xzf` 不需要任何扩展选项。Ubuntu base 里命中 2 条：`perl5.38.2`、`uncompress`。

改写产物按「源文件 sha256 前 12 位」缓存，源没换就复用上一轮。

## 3. `kxxy-glibc` 包装器

`tools/prebuilt/wrappers/kxxy-glibc.sh`，安装时回填 `@DSH_ROOT@` / `@DSH_FILES@`。

```
kxxy-glibc                          进入登录 shell（bash）
kxxy-glibc -c 'apt-get update'      跑一条命令
kxxy-glibc -- /usr/bin/python3 -V    跑一个程序
kxxy-glibc -b /sdcard:/mnt/sd -- ls /mnt/sd
kxxy-glibc -w /kxxy -- ls
```

几个真机上踩出来的必要设置（都是「不写就起不来」，不是优化）：

| 设置 | 不写会怎样 |
| --- | --- |
| `PROOT_LOADER=<root>/libexec/proot/loader` | **任何** execve 都 ENOENT —— loader 被注入进 tracee，找不到它等于没加载器 |
| `PROOT_TMP_DIR=<files>/glibc/tmp` | proot 要在可写目录展开 loader 临时件，默认落到不可写的 `/data/local/tmp` |
| `LD_LIBRARY_PATH=<root>/lib` | proot 自己带 bionic 依赖，裸跑报 `CANNOT LINK EXECUTABLE: library "libtalloc.so.2" not found` |
| `unset LD_PRELOAD` | 宿主的 `libkxxy_exec.so` 会跟着 ptrace 进 tracee，给 glibc 程序套上 bionic 的 exec 重写 |
| `-0` | apt/dpkg 要有 uid 0 的假象 |
| `--link2symlink` | dpkg 用 `link(2)` 建 `status-old`，应用域建不出来 → 装包直接失败 |
| tracee 用 `env -i` 重建环境 | 宿主的 PATH/LD_* 会漏进去，容器里 `ls` 都能找错 |

另外两条只写进文档、没写进包装器：

- **apt 必须加 `-o APT::Sandbox::User=root`**。fake root 下 `_apt` 用户不存在，
  `apt-get update` 会在下载阶段报 `Permission denied`。
- **DNS 靠 bind**：`/system/etc/resolv.conf → /etc/resolv.conf`，否则容器里没有 DNS。

### 3.1 rootfs 落在扩展目录外

`<files>/glibc/rootfs`，不在 `extensions/glibc` 下。这意味着：

- 重装扩展、升级 APK 都不会动它（apt 装的东西全留着）；
- 扩展目录只有 29 MB（池 + 包装器），不会因为「装了 dotnet」而变成 GB 级。

真机实测（装完 julia + dotnet + wkhtmltopdf + sklearn/cv2 之后）：
`extensions/glibc` 29 MB，`files/glibc` 2.8 GB。

> 注意一个只在**手工安装**时出现的行为：`bin/kxxy-glibc` 这条入口软链记录在扩展的

## 7. 已知限制

1. **慢 2–5 倍**。每条 syscall 过 ptrace，I/O 密集（apt 装包、pip 编译）体感更明显。
2. **首次解包约 1 分钟**，之后启动 1 秒内。
3. **容器内也建不出硬链**（`--link2symlink` 把它们降级成软链）。`rsync --link-dest` 这类
   语义在容器里同样不成立。
4. **不是真 root**。`-0` 只是 uid 假象，需要真实权限的东西（起服务、`sudo`、原始套接字、
   设备节点）仍然不行。
5. **不能用 perf**。`perf_event_open` 在应用域本来就被拒，进容器也一样。
6. keras/torch 这类**要找 CUDA / 大页 / 特定内核特性**的库，能 import 但别指望加速。

## 8. 用法建议

- 一次性命令：`kxxy-glibc -c '…'`（不进交互 shell）
- 长任务：`kxxy-glibc` 进去，`apt install` 完再跑，避免每次重建环境
- 与工作区互通：`<files>` 已挂在 `/mnt/kxxy`，直接读写工作区文件
- 想换 rootfs：`KXXY_GLIBC_ROOTFS=<别的目录> kxxy-glibc …`
